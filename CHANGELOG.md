## 1.0.9 — 2026-11-13 (a world by URL; a probe without a scheme)

- **`--world` takes an https URL** (`src/world/source.ts`; `src/cli.ts`, `src/cli-cell.ts`, `src/node/join.ts`; docs/join.md, "Other chains, the same key"). A chain FOGA's table does not know needed a FOGA release to be joinable by name; now the project that runs the chain publishes its address book and a cell anywhere joins it with `foga join --world https://… --rpc <its rpc>`. The URL is fetched once per command, checked to be a world file (`foga.world/1`, a worldId, a chainId, the contracts), kept as a plain file under `~/.foga/worlds/<chainId>-<worldId>-<first 12 hex of its sha256>.json` — two projects that chose one worldId on two chains, or two revisions of one book, are two files, nothing overwritten — and the command runs on that file exactly as on a path — the copy into the cell directory, the genesis store, the doctor's report, all unchanged; the sha256 of the bytes received is printed, the configuration and `join.json` record the URL as `worldSource`. The fields a remote file contributes to local paths (worldId, network, name) are checked against one character set (letters, digits, `.`, `_`, `-`) before anything is written, by the fetch and by the join alike. Only `https://` is accepted (the file names every contract the cell will trust); `http://127.0.0.1` and `localhost` are the one exception, for a rehearsal. `genesis preflight|run|status`, `doctor` (not `--attach`, which takes a configuration), `loop-d run`, `demo demander`, `cell new` and `world verify` take the same URL. The cell card's last line (`joinLine`, `src/node/card.ts`) says `join --chain <name>` only when the world the package ships for that chain is this very world, and otherwise `join --world <the URL this cell was joined from, or its book> --rpc <an RPC of the chain>` — a project's own world on a chain the table knows is reached by its book, never by the chain's name; the MCP replicate prompt gives the same form. Nothing about any chain enters the package for this: the table, the default and the bare `foga join` are unchanged. `test/world-source.test.ts` (2, offline: the path passthrough, the fetch, the kept file by chain, world and content, the two collisions that are not, every refusal, what may name a directory); `test/join.test.ts` gains the URL case over a local server and the provenance in the configuration and `join.json`; `test/node-config.test.ts` the source URL and the card's join line.
- **A cell has one world** (`src/node/join.ts`; docs/join.md). A join into a directory whose cell lives in another world — another worldId or chainId than the book given — went on: the cell kept reading its own `world.json` while `join.json` recorded the worldId of the book passed, so a record of a resume could name one world while the cell ran on another. Such a join is refused now, before anything is read from the chain, with both worlds named (a new cell in another world is `--dir` and `--name`). The same world in a newer revision — a contract added to the published book — is said and not adopted: the cell keeps reading its copy, replacing `world.json` is the operator's deliberate act, and the log says both hashes. `join.json` names the book the cell reads (`world`: worldId, chainId, sha256, file) beside where this join's book came from (`worldSource`); a cell joined by URL keeps that URL in its configuration (`worldSource`, optional), recorded once. `--name` must be able to name a directory when `--dir` is not given. `test/join.test.ts` gains the refusal, the revision and the checks of the fields that name directories (offline: the RPC is a stub).
- **A probe with no KYA scheme in its input reads nothing about standing instead of failing** (`src/genesis/probe.ts`, `src/node/preflight.ts`). `foga node preflight` probes the cell itself and, for a cell without `identity.standing` — every cell at birth — built the probe's input with no `kya` block; the ERC-8419 section dereferenced it, and the `TypeError` was retried as a transport failure until the check failed with "probe: the RPC failed 7 times (Cannot read properties of undefined (reading 'issuers'))" — found on the first readiness check of a cell born on a chain outside the table; it reproduces on anvil (the new test). `kya` is optional in the input now: absent, the ERC-8419 section records `{ schemeId: null, issuers: [], level: null, …, note }` — the same for the demander's run and the cell's, so a report stays comparable — and a programming error inside a section (a `TypeError`, a `RangeError`) is raised at once with its own words instead of being retried six times as the endpoint's silence. Which errors are defects is said precisely (`probeDefect`): the engine's own words — a property of undefined or null, a call of what is not a function, a name never defined, an invalid length — with no `code` and no `cause` attached; the same classes from the transport (undici's `fetch failed` is a `TypeError`) or the data (ethers' `INVALID_ARGUMENT` is a `TypeError`, its `BUFFER_OVERRUN` a `RangeError`) stay transient, retried and then named as the endpoint's, as before. `test/preflight.test.ts` gains the cell without standing: the standing row warns, the probe runs in the worker; `test/runner-refusal.test.ts` the classification.

## 1.0.8 — 2026-11-13 (a join resumes an interrupted birth)

- **A join that finds an account asks whether the birth ended** (`src/node/init.ts` `birthState`, `INIT_STARTED_FACT`, `INIT_COMPLETE_FACT`; `src/node/join.ts`). The third Windows report: a join interrupted after the `FogaCellAccount` was deployed and before the birth's end, then run again, said "born before", skipped the rest of the birth and failed at the first skill mint with `LengthMismatch()` — the account refusing every act until its safety binding is presented (ASF: one clause in the requirement, no binding). The join decided "born" from the account alone, and the account is saved the moment it is deployed so that a resume has it. The birth now records its start (once; a resume keeps the first) and its end (after the readiness check) as facts in the cell's store; `birthState` reads `unborn`, `born` or `interrupted` from them — a start without an end is interrupted whatever the configuration already holds — and the join resumes an interrupted birth from the journal before anything else, nothing sent twice (`foga cell init` on such a configuration did the same by hand, as the reporter found). A cell born before 1.0.8 has neither fact and is read from the fields the birth fills late (agent id, binding, record, unit); an account whose deployment the store never journaled (a configuration copied without its store) counts as born. `test/join-interrupted.test.ts` (anvil): a birth interrupted right after the account, and one interrupted after the enrollment with every late field already filled — both resumed by the next join with the same account, the channel opened on the resume, the skills minted, a third join sending nothing; 138 tests.

## 1.0.7 — 2026-11-11 (a tender's submissions read as one)

- **The count and the entries of a tender are read together** (`src/core/tenders.ts` `Tenders.submissions`; `src/tools/common.ts`, `src/node/meditation-cycle.ts`, `src/demo/loop-d.ts`). CI's Loop D run failed three times in nine on one day with `TaskToken: nonexistent submission` from the orchestrator's `settledOnChain`: `submissionCountOf` had answered 1, and `submissionOf(…, 1)` at the same block tag reverted. Reproduced outside FOGA with a counter contract: anvil 1.7.1 under automine answers an `eth_call` tagged with the current head from a state that already holds the next block, about one call in a thousand under continuous mining — two consecutive reads at the same tag, two values — and the pinned provider (docs/kernel.md) cannot help with a node that answers *ahead* of the tag. Every count-then-walk loop now goes through `Tenders.submissions`: the count and the entries are read as one, and when the count announces an id that the next read calls nonexistent the walk starts over from a fresh count (three times at most, then the error is raised; any other revert is raised at once). `readTender` — behind every `tender_inspect`, pre-check and submit — the maintenance cycle's in-flight check and the Loop D orchestrator use it, and `readTender` reads one call less. `test/tenders-read.test.ts` (5, offline) scripts the race; 137 tests. Nothing changes for a running cell beyond the read.

## 1.0.4 — 2026-11-10 (the first Windows run: the skill worker's path, and the card's ERC-8004 registry)

Two findings from testing 0.7.4 on Windows (quickstart and MCP ran; the genesis stopped in T3), both still present in 1.0.3 and both fixed here; nothing else changes.

- **The skill worker starts on Windows** (`src/genesis/skill-runner.ts`). The worker module's path was taken from the URL's `pathname`, which for a `file:` URL on Windows is `/C:/Users/…` — Node read it as a path on the current drive (`C:\C:\Users\…`) and the worker died at its spawn with `MODULE_NOT_FOUND`, so T3's `foga-probe` run and every `skill_run` failed. The path is `fileURLToPath` now, which also decodes a directory with spaces on every platform. The worker's environment, the PATH alone until now, carries on Windows the variables Node needs to start and to reach the network (`SystemRoot`, `windir`, the temp directory, `PATHEXT`, `COMSPEC`); still nothing that could carry a key. `scripts/alias-sync.mjs` had the same `pathname`.
- **The card names the ERC-8004 registry** (`src/node/card.ts`). `foga cell card` looked the registry up under `identity8004/IdentityRegistry`; the world files key it `identity8004`, so `identity.registry` was `null` in the JSON and the `identity` line said no registry on every platform since the card exists (0.7.0). The on-chain registration was never affected. `test/specification.test.ts` asserts the card's registry against the kernel's.

## 1.0.2 — 2026-11-10 (a joined cell's skill copy follows the program's package)

- **`skill_update` moves a joined cell's token too.** A cell born by `foga join` carries its own copy of the skill packages (`skills/` in its directory: their hashes are what the chain holds, and the files stay where the cell is rather than where a version of the program is installed), so after 1.0.0 moved `foga-probe` to 2.0.0 such a cell's copy still agreed with its token and `skill_update` answered "nothing to update" — the program's 2.0.0 package was never consulted, and the token stayed on the old package (the runner produced `foga.probe/2` regardless: the program runs the skill, the token describes it). Now, when the directory's package is what the token holds and the program's package of the skill differs, the update commits the program's package (version + 1, the old package as predecessor, the ERC-8444 record re-committed) and, once the chain holds it, refreshes the cell's copy from the program's package, the old copy kept beside it as `skills/<name>.before-<hash>`; the dry run names the package it would refresh from and touches nothing — neither the directory nor the configuration, which 1.0.0's dry run wrote as if the update had been sent. A copy the operator changed is committed as it is, as before; a copy newer than the program's (an older program run against a cell that saw a newer one) is left alone, with the reason; a cell whose skill directory is the program's own (the quickstart's, the OG's checkout) has nothing to refresh and behaves as before. The output gains `refreshedFrom` and `previousCopy`. On Sepolia this is `cell-fd22`'s step: `npx -y @finchtech.ai/foga cell skill update --skill foga-probe …` once 1.0.2 is published (docs/og-deployment.md); the OG holds `finch-extract-verify` alone and needs none.

## 0.7.4 — 2026-11-06 (the probe tells a revert from an endpoint that did not answer; a run the endpoint failed is tried again; a block an endpoint no longer serves)

- **A failed `eth_call` is not a revert until the node says so** (`src/kernel/provider.ts`, `isRevertError`, `chainAnswered`, `rpcErrorText`; `src/genesis/probe.ts`, `transientRpcError`). Why tenders 48 and 49 of the two-machine Sepolia handshake were submitted and then refused at settlement (`TaskToken: verification failed`) when 0.7.2 had made the probe retry transport failures. The cell's probe ran an hour and more after each mint (the releases between them were the gap), on the public endpoint, for a block that old — and the endpoint, a full node that keeps the state of its recent blocks only, no longer served it: `eth_call` at block 12075502 answers `historical state … is not available` (the balance at that block is still served; the contract state is not). ethers turns *every* JSON-RPC error of an `eth_call` into a `CALL_EXCEPTION` ("missing revert data") — a revert, but just as well this, a node that has not reached the block, a rate limit, a timeout — and the 0.7.2 rule read the code alone, so each refusal was taken for the chain's answer and written as a null section, where the demander, probing a fresh block at mint time, had values. The rule now is the one the kernel's pinned provider already applied to its own reads: a revert is told by its return data (a custom error's selector, a reason string), by a reason ethers decoded, or by the node's own words (`execution reverted`, nethermind's `VM execution error`); data of another shape than the ABI's (`0x` from an account without that code at that block) is the chain's answer too; everything else is the endpoint's and is retried, and if it persists the run fails — never a report with a hole in it. The probe's inner catches (a burned skill token, a subject that is not a cell account) consult the same rule, so a transport failure inside them is retried rather than read as "burned" or "no status"; the block header is asked again when a node answers null for it. `test/runner-refusal.test.ts` builds the errors as ethers does (`AbiCoder.getBuiltinCallException` with the node's error in `info`) for geth, erigon, reth, anvil, nethermind and besu reverts, for `missing trie node`, `header not found`, `historical state … is not available`, a rate limit and an unexplained failure.
- **A block the endpoint does not serve is read elsewhere, or left** (`src/genesis/probe.ts`, `PROBE_STATE_GONE`, `RECENT_BLOCKS`, `blocksBehind`; `src/tools/tenders.ts`, `probeThroughEndpoints`). When the node's words say it has no state for the pinned block, the probe says so (`probe: the endpoint does not serve the state of block N (k blocks behind its head …)`) instead of asking the same endpoint again, and the cell asks the chain's other public endpoints in turn (`src/core/chains.ts`), one of which may be an archive, saying which one answered. When none does: a block still young (128 behind the head or less — a geth full node's window) is one the endpoints have not caught up with, a transient failure tried again later; an older one is left — the run stands failed with the remedy in its words (an archive endpoint: `--rpc <url>`, `SEPOLIA_RPC_URL`), and the tender to a cell that was there. The demander picks its probe block within 20 blocks of the head rather than 50 (`src/demo/demander.ts`), inside any endpoint's window with the cell's tick to spare.
- **A run the endpoint failed is no verdict on the tender** (`src/tools/common.ts`, `runJobId`, `transientRunFailure`, `RUN_ATTEMPTS`; `src/node/runner.ts`, `runFailureLapsed`). A skill run that ends in `probe: the RPC failed …` is the endpoint's failure; the runner's situation holds the tender back for a minute (as a transient refusal, 0.7.1) and then reads it as open again, and the next `skill_run` for the same request is a new job (`…:r2`, `…:r3`, up to five attempts), so the catalog does not answer it with the old failure. A run that failed on its merits — a missing input, a skill the node does not run, a block no endpoint serves — stands as before, and so does the attempt past the limit.

## 0.6.0-alpha.2 — 2026-11-02 (Phase 3a-2: the capability catalog and the node)

The kernel of 3a-1 becomes a node other agents can call: a catalog of capabilities that is the one authorization boundary, a policy engine applying the cell's own rules, decision records for every attempt to act, and the runtime of a cell that lives outside the genesis. The CLI is the first entrance; MCP and HTTP (3b) and A2A (3d) are further entrances onto the same catalog. docs/node.md.

- **The capability catalog** (`src/tools/`): 28 capabilities on the Loop D path (reads `world_describe`, `identity_resolve`, `tender_list`, `tender_inspect`, `skill_list`, `skill_inspect`, `cell_status`, `operation_status`, `job_status`, `operation_list`, `decision_list`, `evidence_export`, `kya_check`, `safety_status`; acts `tender_precheck`, `skill_run`, `tender_submit`, `tender_settle`, `credit_withdraw`, `tender_mint`, `tender_fund`, `skill_mint`, `aid_heartbeat`; admin `operator_rotate`, `guardian_suspend`, `guardian_resume`, `binding_present`, `identity_transfer`). Each declares its action (read / build / act / admin), the visibility of its data (public / caller / operator) and whose act it is (none / the cell / the account a build is for), with zod input and output schemas published as JSON Schema 2020-12. Three execution modes for a write: `simulate` (every check and a dry run, a decision record, nothing sent), `build` (the calls for someone else's account, `as`), `act`.
- **Three checks, in the catalog, for every act** (`Catalog.invoke`): call permission (visibility, level for the mode, the signer's key present for an admin act), business authorization (the capability's plan judged by the policy engine, `src/node/policy.ts` — gates `safety`, `skill`, `policy`, `verifier` — and the catalog's `budget` gate over the last 24 hours of value and fees plus open reservations, the per-operation cap and the concurrent commitments), wallet permission (the first step simulated from its signer; the account decides again on chain). The first refusal ends the attempt; an act that passed is recorded as allowed before anything is sent, and a failure after that is a second record at gate `execution`, naming the operation.
- **Decision records** (`decisions` table; `OperationStore.decide`, `decisions`, and the store summary): `{entrance, caller, capability, mode, inputHash, verdict, gate, reason, jobId, operationId, model}` for every act attempt in every mode; reads leave none; a model's words never enter one, only their hashes. `decision_list` for a caller's own, `evidence_export` (`foga.node-evidence/1`) for the operator's whole view.
- **Jobs and operations.** A job is created only once every gate has passed, so a refusal leaves a decision and nothing else; a job's id is the caller's `jobId` or one derived from the semantic input — a tender's n-th completion by the cell is `tender:<tokenId>:c<n>`, so a second legitimate completion is another job; the same job is answered from the store (`idempotent`), a failed job answers with its failure, the same job under another request is a `conflict`; an interrupted job continues. `tender_precheck` is ephemeral: a decision, no job. Operation keys are `job:<jobId>:<step>`, each bound to the request's hash, the capability, the caller and the cell (3a-1's bindings). `Cell.execute` and `Cell.admin` take a binding; `OperationStore.budgetBooks` keeps value and fees apart; `countJobs` counts the running commitments.
- **The cell configuration** (`src/node/config.ts`, schema `foga.cell-config/1`): identity, presence, skills (held and offered, the packages and input directories), policy (budget and tender rules), runtime; validated with zod, paths resolved against the file, written back by `init`, `migrate` and `skill_mint`.
- **The node** (`src/node/node.ts`): the kernel opened on the cell's world and store with only the keys this process holds (the operator's for a node, the owner's or the guardian's for a one-shot admin command), the cell handle, the policy's view of the store. It refuses a revision-1 account, an account whose operator or owner differs from the config, a key that disagrees with the config, and a store that belongs to another cell.
- **Birth and migration.** `foga cell init` is T1 for one cell from its config (the owner's act; the specification published when the config names none; the operator's allow-list from the standalone scope groups; every step a keyed operation, so it resumes and replays); `foga cell migrate` is T9 for one cell (a new revision-2 account with a fresh operator if given, the agent moved as the owner's act, the takeover and retirement, record, document and unit, the skills following with their records recommitted, the old balance swept). `src/node/init.ts`, `src/node/migrate.ts`.
- **The watchers** (`src/node/watchers.ts`; `foga node tick`, `foga node watch`): heartbeat when under half the window is left, discovery of open tenders (`tender-discovered`), settlement of pending submissions whose answer a run holds and withdrawal of credit, a `safety-changed` entry when the verdict changes — through the catalog like any caller, in a node environment (the operator key alone; an environment that also holds the owner's or guardian's key is refused: `FOGA_OWNER_KEY[_FILE]` and `FOGA_GUARDIAN_KEY[_FILE]` join the forbidden list). `loadRoleKey` reads those two for the CLI's one-shot commands.
- **The CLI** (`src/cli-cell.ts`): `foga cell list | schema | new | init | migrate | status | <capability> [--mode] [--<field> <value>] [--json]`, `foga cell owner … | guardian …`, `foga node tick | watch`; refusals exit 2 with `{ok: false, gate, reason, decisionId}`; `--caller`/`--level` call as another caller would. `inputDir` added to the skills block; an inline document (a `data:` URI in a task's input) is written beside the cell's store and read from there.
- **Tests.** `test/node-cli.test.ts` (anvil; the 3a-2 gate: a world, a cell born by `foga cell init` without the genesis, standing from the issuer, two skills minted, the seven Loop D cases a–g through the CLI — a and b taken and settled, c `skill`, d `policy`, e `verifier`, f `safety` then allowed after the resume, g `budget` — idempotency, conflict, build mode, the acceptance matrix read from the records and the chain, `foga node tick` in a clean and a mixed environment, the migration to a new account with a fresh operator), `test/policy.test.ts` (6), `test/catalog.test.ts` (4), `test/node-config.test.ts` (2). 74 unit tests with anvil present (73 without), the Foundry suite and the genesis unchanged and green.

Nothing in it changes what the genesis proves; the scenario gains six operations that open each cell's operator scope.

- **FogaCellAccount revision 2** (`ACCOUNT_VERSION = 2`; the bundle is rebuilt, hash `0xb09770ec…`; only `foga:FogaCellAccount`'s code changed — the predicate adapter's `immutableReferences` carry renumbered AST ids from the same compilation unit, its bytecode is byte-identical). The operator may call only the (target, selector) pairs the owner allow-listed — `setOperatorAllowed`, `setOperatorAllowedBatch`, `operatorAllowed`, `OperatorAllowedSet`; a call outside the list reverts with `OperatorNotAllowed` — and never an asset-moving selector (`transfer`, `transferFrom`, the ERC-721 and ERC-1155 `safeTransferFrom`s, `safeBatchTransferFrom`, `approve`, `setApprovalForAll`, `increaseAllowance`, `permit`: `OperatorAssetSelector`, also when the owner tries to allow-list one). ERC-1271 signatures by the operator are off by default (`setOperatorMaySign`, `operatorMaySign`, `OperatorSigningSet`) and, when on, require the safety gate to be satisfied, not just the operator unexpired. The owner's calls are unchanged. 17 Foundry tests (two new, one extended). docs/cell-account.md. The 0.5.0 cells on Sepolia are revision-1 accounts; the OG instance moves to a revision-2 account in 3d.
- **The genesis opens the scope it uses.** `src/genesis/operator-scope.ts` names the scope in groups after what a cell does (identity, standing, skills-provider, labour, demander, organization-member, organization-coordinator, service-provider, service-client); T1 sets each cell's list in one batch after `setOperator` (`T1.<X>.scope`, recorded as a fact), T4 opens the swarm's decision adapter and account to B's operator when they exist (`T4.B.scope.*`), T9 sets A-prime's (`T9.Aprime.scope`), and A's identity and skill move to A-prime signed by A's owner, which is the only key the account lets move an asset. Scenario version 5: 193 operations on anvil (187 before), 201 in the attach rehearsal (195), 166 and 171 checks as before; the ERC-8004 selectors come from the module ABI so an attached official registry resolves too.
- **Transaction manager.** The number of fee replacements is counted on the operation's row and persisted (`replacements`): the old loop recursed into the wait and started the count again on every timeout, so the "three replacements" limit never held across a resumed run. A fee cap (`maxFeePerGasCap`, per manager or per request) clamps the first send (`fee-capped`) and refuses a replacement that would pass it (`replace-capped`); at the limit or the cap the pending transaction is waited for as it is (`replace-limit`), and the row stays `sent` for the next run. One signer's operations now run one at a time, in order, whoever asks concurrently; other signers run beside it. A key is bound to the canonical hash of its request (`OpBinding`): the same key with another request is `OperationConflict` before the chain is touched, a key claimed without a hash takes the first it is asked with. A failed operation answers with its failure on every later send (`replayed-failure`) until retried explicitly (`retryFailed`: the genesis driver retries, a public caller does not; `retry` puts the row back to `prepared` and keeps the fee the reverted attempt cost); the hashes of a retried attempt are not waited for again. Rows record the value a transaction carries and the fees paid (cumulative over attempts); `budgetUse(signer, since)` gives what settled operations spent and what open ones reserve. An RPC failure while waiting leaves the row `sent`.
- **Store.** New columns on `ops` (replacements, request hash, capability, caller, cell, value, fee cap, gas cost; an older store gains them on open) and a `jobs` table (`createJob`, `updateJob`, `getJob`, `jobs(caller)`: the business unit a caller asks for, with its input hash, state, result and the operations it made; the same id with another input is a conflict). `transaction(fn)` for a claim and its reservation; nested calls join the outer transaction. The kernel checks the store's world id and chain id against the world file, not just block 0, and completes an older store's identity on its first open.
- **Keys.** A node holds one key: `src/node/keys.ts` loads it from `FOGA_OPERATOR_KEY_FILE` (a regular file owned by the node's user, mode 0600 or tighter) or `FOGA_OPERATOR_KEY`, exactly one of the two, and refuses to start when the environment also carries `FOGA_MNEMONIC`, `FOGA_MNEMONIC_FILE`, `FOGA_DEPLOYER_PK` or any `FOGA_KEY_<ROLE>` — the refusal names the variables, never their values. `foga keys export --role <role> [--out <file>]` writes one role's key to a 0600 file from the operator's phrase; `foga keys check` reads the current environment as a node would. The genesis still derives its twelve roles as before.
- **Skill worker.** `src/genesis/probe-worker.ts` is replaced by `src/genesis/skill-worker.ts`, one worker for both executors: `finch-extract-verify`'s extraction now runs out of process too (T5 and T7), a document is accepted only inside the input directory and a fields file only inside the skills directory (real paths).
