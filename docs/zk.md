# The ZK paths of ERC-8419

FOGA runs both proving patterns the KYA standard describes: the credential pattern, with the upstream circuit, and the predicate pattern, with a circuit of its own. Both are driven from the kernel through `prover/run.cjs` (docs/kernel.md) and admitted on chain through `KYARegistry.attestWithProof` with an `IKYAVerifier` adapter; neither puts a private fact on chain.

| | credential pattern (`S_cred`) | predicate pattern (`S_pred`) |
|---|---|---|
| statement | "an attestor of the admitted issuer set signed this standing level for me" | "at least K task-completion records about me, signed by a source of the committed set, are Accepted inside [t0, t1]" |
| circuit | `kya_public_v1` (kya-standard, vendored) | `kya_predicate_count_v1` (`zk/circuits/`, FOGA) |
| hidden | the issuer, the credential | the records, their number, the source |
| disclosed | subject, level, claim digest, expiry, issuer-set root, scheme, admission domain, epoch | subject, challenge, window, K, source-set root, result bit, scheme, admission domain, epoch |
| adapter | upstream `Groth16KYAVerifierAdapter`, FOGA's instance pinned to FOGA's issuer set | `contracts/src/zk/Groth16PredicateKYAVerifierAdapter.sol`, pinned to FOGA's source set |
| level issued | the level signed (4 in the genesis) | 1 when the rule holds; a false predicate is rejected, never recorded |
| nullifier scope | (scheme, admission domain, epoch) | (scheme, admission domain, epoch, challenge) |
| proving material | `foga vendor sync` (upstream build) | `npm run zk:predicate` (built here) |
| where in the genesis | T1, cell A | end of T3, cell A, over its first accepted completion |

## The predicate circuit

`KYAPredicateCountV1(n, depth)`, instantiated with 8 record slots and a source set of depth 16 (about 87 000 constraints). A record is `(subjectKeyHi, subjectKeyLo, taskRef, status, timestamp)`: the subject's key split in two 128-bit halves, a 128-bit identifier of the completion (the source's own hash of chain, task contract, token and submission), a status code (1 = Accepted) and a timestamp. The source signs `Poseidon(5)` of the record with EdDSA over Baby Jubjub; its public key is a leaf of a Poseidon Merkle tree, the source set, built exactly like the credential path's issuer set.

The circuit checks, for every present slot, that the signature verifies under the source's key and that the message is about the public subject; that present slots form a prefix and carry strictly increasing `taskRef`s (no record counts twice); that the source's key is in the set whose root is public; and it counts the present records that are Accepted and inside `[t0, t1]`. The outputs are the nullifier `Poseidon(secret, schemeId, admissionDomain, epoch, challenge)` and `result = (count >= k)`. `schemeId` and `admissionDomain` are fed by the adapter from its own arguments, as in the upstream circuit, so a proof is bound to the rule and to the admitting registry; `epoch` is enforced by the adapter against block time within a grace window; the `challenge` is the relying party's freshness value, so a proof answers one request.

Public signals, in snarkjs order: `[0] nullifierHi [1] nullifierLo [2] result [3] subjectKeyHi [4] subjectKeyLo [5] challengeHi [6] challengeLo [7] t0 [8] t1 [9] k [10] sourceSetRootHi [11] sourceSetRootLo [12] schemeIdHi [13] schemeIdLo [14] epoch [15] admissionDomainHi [16] admissionDomainLo`. The adapter's `publicInputs` layout is `abi.encode(bytes32 subjectKey, bytes32 nullifier, bytes32 challenge, uint64 t0, uint64 t1, uint16 k, bytes32 sourceSetRoot, uint64 epoch, uint8 result)`; `claimDigest = keccak256(abi.encode(challenge, t0, t1, k, sourceSetRoot))` commits to the disclosed rule; `anchor = sourceSetRoot`; `expiresAt = block.timestamp + validity`.

What the proof establishes is a fact about a range of records under one source set, not that the agent is trustworthy; the relying party chooses the rule and the source set it is prepared to believe.

## Building the proving material

```bash
npm run zk:install      # the proving libraries (prover/)
npm run zk:predicate    # compile the circuit and run the development ceremony: 10-60 minutes, once
```

`prover/build-predicate.mjs` compiles the circuit with the WASM build of circom (`circom2`), creates a powers-of-tau of 2^17 with a fixed public beacon (`keccak256("foga.kya-predicate-count-v1.development-ceremony")`, 10 iterations), prepares phase 2, runs the Groth16 setup and a phase-2 beacon with the same value, and exports the verification key and the Solidity verifier (`contracts/src/zk/Groth16PredicateVerifier.sol`, contract renamed, generated by snarkjs under its own license header). Everything is deterministic, so anyone can rebuild the same keys bit for bit and CI checks that the regenerated verification key and verifier equal the committed ones.

That determinism is also why this is a **development ceremony**: its randomness is public, so the proving key could in principle be used to forge proofs. It is fit for the genesis and for tests; before any use where a forged proof would matter, the circuit needs a real multi-party ceremony and the adapter a new verifier. The committed files make this explicit in their headers.

Outputs live in `zk/build/` (gitignored except `verification_key.json`): the r1cs, the witness generator (`kya_predicate_count_v1_js/`), the proving key (`kya_predicate_count_v1_final.zkey`, about 65 MB) and the powers of tau. `FOGA_ZK_PREDICATE_DIR` points the prover at another directory.

## Running without it

`foga genesis run --zk auto` (the default) records `T0.zk.predicate = off` when the material is missing: the scheme `S_pred`, its verifier and its adapter are still deployed and registered in T0 (the verifier contract is committed), and the predicate checks of T3 are recorded as skipped. `--zk require` refuses to start without it. A store decides once; a later run with the material present does not change a store that started without it.

## Keys and secrets

The source key is derived from W's key (`keccak(label, key)`), the prover secret from the cell's operator key and the scheme id; nothing is stored. The prover bridge keeps the roles apart: `record.sign` takes the source's key and one record; `root` takes source keys and returns the set; `predicate.prove` takes public material, the records with their signatures and the prover's secret only.
