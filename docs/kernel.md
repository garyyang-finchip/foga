# The cell kernel (foga-kernel)

`src/kernel/` is the deterministic part of a node: it holds the keys, decides what to send, sends each thing once, and keeps the record a reviewer or a restarted process needs. There is no model inside it. `src/core/` (foga-core) underneath is one module per ERC — views, calldata builders, event decoders, canonicalization and the DAG-CBOR skill packager — with no transaction management of its own.

## Pieces

| File | What it is |
|---|---|
| `kernel/store.ts` | `OperationStore`: the operation table (each row bound to the request that claimed it), the job table, the decision records of the node (docs/node.md), scenario facts and an append-only journal in one SQLite file (`node:sqlite`, WAL, `synchronous=FULL`). `:memory:` for tests. |
| `kernel/tx.ts` | `TxManager`: exactly-once sending by idempotency key, one operation at a time per signer, receipt recovery, re-send and fee-replacement rules with a persisted limit and a fee cap, fault injection. |
| `kernel/cell.ts` | `Cell`: one FogaCellAccount driven through its owner and operator keys (`deploy`, `execute`, `admin`, `adoptBinding`, `status`). |
| `kernel/kernel.ts` | `Kernel`: a world, a store, the signers, the ten modules opened on that world, `call` / `deploy` / `transfer`, facts, `memo`, evidence. |
| `kernel/errors.ts` | `RevertDecoder`: custom errors across every world ABI, `Error(string)`, `Panic`, and `CallFailed` unwrapping. |

## Exactly once

Every chain write has a key chosen by the caller (`T3.A.submit`). `TxManager.send` runs this sequence for a new key:

0. take the signer's turn — a signer's operations run one at a time, in the order they were asked for, whoever asks concurrently (a resumed genesis step and a public caller, two public callers): the nonce is taken, the transaction sent and its receipt awaited before the next operation of that signer begins. Different signers run side by side. A failure releases the turn; a pending transaction holds it, which is what the chain would do with the nonce anyway;
1. fix the nonce (`getTransactionCount(signer, "pending")`);
2. build the request — the builder receives the nonce, so a deployment can predict its own address;
3. estimate gas on the pending state and add a margin (25 % + 20 000): the inclusion state differs from the estimate's at least by the block timestamp, and an `SSTORE` that was a no-op during the estimate (a heartbeat written in the same second) costs 2 900 more when the second ticks;
4. sign, compute the hash, **write the row as `sent` with hash, nonce and the value the transaction carries**;
5. broadcast;
6. wait for the receipt (120 s by default); write the row as `confirmed` with block, gas, log count and the fee paid, or `failed` with the reason (and the fee paid, when the transaction was mined and reverted).

Step 4 before step 5 is what makes a crash recoverable: whatever happens afterwards, the store knows which transaction may be out there.

When the wait runs out, the chain is asked what became of the transaction. Still pending (a public chain whose base fee rose after the quote): it is **replaced** — the same payload under the same nonce, signed again with fees a third above the pending ones, recorded as the operation's new hash (`replaced`, naming the hash it replaces) and waited for in turn. The number of replacements is counted on the row, so the limit (`maxReplacements`, three by default) is for the operation's life: a run that stops after the third and a run that resumes an hour later do not start the count again — the resumed run finds the transaction pending, records `replace-limit` and waits for it as it is. A fee cap (`maxFeePerGasCap`, per manager or per request) bounds both the first send — a quote above the cap is clamped to it (`fee-capped`) — and every replacement: one that would pass the cap is not made (`replace-capped`), the pending transaction is waited for, and the row stays `sent` for the next run. Gone from the pool with the nonce still free: broadcast again as it was (`resend`). Gone with the nonce consumed by something else: `OperationAmbiguous`. Every hash an operation's current attempt ever had is in the journal, and the receipt of any of them completes it — the nonce makes them mutually exclusive, so exactly one can be mined. On a local chain a timeout almost always means the node is starved by another process (a proving-key build), not fees; the replacement is harmless there and the message says what to look for.

A key is **bound to its request**. `prepare(key, kind, signer, binding)` claims the key together with the canonical hash of the request that produced it, the capability, the caller and the cell, and the value and fee it reserves; the claim and its reservation are one SQLite transaction. The same key with the same request hash is the same operation and is answered from the store; the same key with another request hash is refused (`OperationConflict`, naming both hashes) before anything touches the chain — a key is never a way to get someone else's result, nor to send a second transaction under a first one's name. A claim without a hash (the genesis driver) binds nothing and takes the first binding it is later asked with. Keys name the business fact they settle, not a permanent slot: `tender.submit:<tokenId>` is the submission of that tender, and a second submission of the same tender is a conflict by design.

A **failed** operation is the operation's answer. A key whose estimate reverted, or whose transaction was mined and reverted, answers with that failure again on every later `send` (`replayed-failure`): nothing is sent anew because a key was asked for twice. Only an explicit retry (`retryFailed` on the request or on the manager) starts a new attempt — the row goes back to `prepared` (`retry`, keeping the failure in the journal and the fee it cost on the row), and the new attempt takes a new nonce; the hashes of the failed attempt are not waited for again. The genesis driver retries, because its failures are fixed between runs; a public caller does not, because its failure is a verdict it must read.

`budgetUse(signer, since)` sums what a signer's settled operations spent since a time — the value moved by confirmed ones and the fees paid by confirmed and reverted ones alike — and what its open operations (`prepared`, `sent`) still reserve (value plus fee cap). That pair is what a cell's budget is checked against before a new claim (Phase 3). Fees are cumulative over an operation's attempts.

### What a resumed run does with a row

| Row status | The chain says | Decision |
|---|---|---|
| `confirmed` | receipt for the hash exists | answered from the store; the receipt is re-read for its logs (`replayed`) |
| `confirmed` | no receipt for the hash | the store and the chain have diverged: refuse (`OperationAmbiguous`) |
| `sent` | a receipt exists for any hash the operation had | finish from the receipt, nothing re-sent (`recovered-receipt`) |
| `sent` | the transaction is known and pending | replace it with higher fees under the same nonce and wait for whichever is mined (`recovered-pending`, `replaced`); at the replacement limit or the fee cap, wait for it as it is (`replace-limit`, `replace-capped`) |
| `sent` | unknown hash, the signer's nonce still equals the row's | the transaction never reached the chain: re-send with the same nonce (`resend`) |
| `sent` | unknown hash, the signer's nonce has moved past the row's | something else consumed the nonce; the outcome cannot be decided by code (`OperationAmbiguous`): never retried automatically |
| `failed` | — | answered with the recorded failure (`replayed-failure`); a new attempt only with `retryFailed` (`retry`) |
| `prepared` | — | claimed but never signed (a crash between the claim and the signature): sent as a new operation under its binding |
| none | — | a new send |

An RPC failure while waiting (a node that cannot answer a receipt lookup) is not the operation's failure: the error propagates, the row stays `sent`, and the next run resolves it by the table above.

A store belongs to one chain instance and one world. It records the hash of block 0, the chain id and the world id the first time it opens (an older store that recorded only the block-0 hash gains the other two on its next open); a later open against a chain with a different block 0 (a restarted anvil), another chain id or another world file is refused with both identities named rather than replaying a history into a world where it never happened.

### Jobs

Operations are chain writes. A **job** (`jobs` table: `createJob`, `updateJob`, `getJob`, `jobs(caller)`) is the unit of business work a caller asks for — a tender taken, a skill run, a document published — with its input and the hash of it, its state (`accepted`, `running`, `done`, `failed`, `rejected`, `cancelled`), its result or error and the keys of the operations it made. The same job id with the same input is the same job; with another input it is a conflict. A caller sees its own jobs; the operator sees every job. The genesis has no jobs: it is one driver running one scenario. The node answers a request with a job id, the job holds the operation ids, and a reviewer reads the chain from the operations; how the node derives job ids, when it creates a job and what it records about every attempt is in docs/node.md.

### Fault injection

`--crash-before <key>` exits the process (code 75, `EX_TEMPFAIL`) right after the row is written as `sent`, before the broadcast; `--crash-after <key>` exits right after the broadcast, before the receipt is read. Both leave the store in the state a real crash would, and the next run must resolve it by the table above. CI crashes the genesis after the broadcast of `T3.A.submit`, resumes it to T9 (exactly one `recovered` operation, the tender with exactly one submission) and then replays the whole store (nothing sent). The rest of the table is covered offline: `test/tx-semantics.test.ts` drives the manager against an in-process JSON-RPC chain (`test/mock-chain.ts`) through the replacement limit across a restart, the same key under two requests, the reverted operation and its explicit retry, the estimate that reverts, one signer's queue and another signer beside it, the fee cap at the first send and at a replacement, the failing receipt lookup, the transaction a pool forgot and the nonce something else consumed; `test/tx-replace.test.ts` makes one replacement against a real anvil when one is installed.

## Facts and `memo`

Values a later step needs (ids, addresses, hashes) are facts in the store, written when known. Values that enter a transaction and depend on the clock or on chain state at run time — deadlines, the probe block, a Groth16 proof bound to an epoch — go through `kernel.memo(key, compute)`: computed once, read back on every later run, so a resumed run rebuilds exactly the inputs the recorded transactions were made from. Rebuilding them from the clock again would make the store's account of a replayed operation disagree with the chain.

## Chain time

`kernel.advanceTime(seconds, why)` lets a window pass. On anvil it moves the clock (`evm_increaseTime`, then a block) and writes a `time-skipped` journal entry with the interval and the reason, so a skipped window is visible in the evidence; on any other chain it waits for real time (`time-waited`, polling the block timestamp every 5 s). The genesis chooses realistic windows on a local chain and short ones elsewhere (docs/genesis.md).

The provider polls a local node every 250 ms and a public endpoint every 4 s: a shared, rate-limited endpoint that makes a block every 12 s is asked a few times per block, not several times per second.

A public RPC URL usually fronts a cluster whose nodes import a block at slightly different times, so a read made right after a receipt can land on a node that has not seen the block yet (on Sepolia the roster of a swarm read as not met one second after its third `join` confirmed, and a call opened in one block was unknown to the gas estimate of its delivery in the next). The kernel therefore reads what it has written: its provider (`kernel/provider.ts`, `PinnedProvider`) keeps the highest block it has seen in a receipt, a block header or a block number, and sends every state read made at "latest" — `eth_call`, `eth_estimateGas`, balances, code, storage — at that block instead. A node behind the pin answers with an error rather than with stale state, and the request is retried (up to 60 s) until a node that has the block answers; a contract's revert is an answer and is never retried. When the retries run out, the endpoint's head is sampled again: a pin that came from a node ahead of the rest is lowered to the head the endpoint reports and the read made there, once; otherwise the error is raised with the node's own words and the run stops where it is, to be resumed from its store. A read at "latest" is never substituted — the node that refuses an explicit block may be the one that is hours behind, and a stale answer fails checks that hold on chain (seen on Sepolia: a swarm read as ACTIVE after its conclusion, a document digest read as the version before its update). The kernel journals these events (`pinned-read`). Explicit block tags (the probe's fixed block), "pending" (the nonce) and everything that is not a state read pass through unchanged, and the pin moves forward with every receipt and with the block headers read while waiting for a window, so time-dependent views are read at the current block. The pin starts at the chain's head when the kernel opens, so a replayed run — which reads back old receipts and sends nothing — reads the chain as it is now, not as it was at each step. On a single local node the pin is simply the node's tip. The transaction manager additionally waits, after a receipt on a public chain, until the endpoint reports that block twice in a row (`visibility-waited` when it had to). The journal of the Sepolia run (`deployments/sepolia.genesis.example.json`) has the whole story in order: the two `estimate-failed` entries of the lag, the `pinned-read` entries with the nodes' refusals in their own words, one `recovered-receipt` for a transaction mined while the process hung, and the `time-waited` entries of the windows.

## Gas

Every estimate gets a margin (see above). A call whose outcome depends on the gas it is given — the SwarmRegistry's `challenge`, which treats an eligibility module's `false` returned with little gas left as unevaluable — takes an explicit `gasLimit` through `kernel.call`, because an estimate stops at the first non-reverting path, and "unevaluable, nothing changed" is one.

## Evidence

`kernel.evidence(step, label, values)` records what a reviewer needs per step (addresses, ids, hashes, transaction hashes, run receipts). The genesis writes it, together with the checks, facts, operation summary and the journal of the run, to `deployments/<world>.genesis.json` (`foga.genesis-evidence/1`). `deployments/local.genesis.example.json` is a committed run. The doctor consumes that file for its fifth layer (docs/doctor.md).

## Keys and funds

The kernel's signers are named by role (`W`, `G`, `owner.A`, `operator.A`, …). The genesis plays every part, so it loads all twelve: the first twelve accounts of one BIP-39 phrase (`src/genesis/roles.ts`), anvil's well-known phrase on anvil, so every local run uses the same addresses; on any other chain the phrase in `FOGA_MNEMONIC` or in the file named by `FOGA_MNEMONIC_FILE` (`foga keys new` writes one, `foga keys show` lists the addresses), with `FOGA_KEY_<ROLE>` (`FOGA_KEY_W`, `FOGA_KEY_OWNER_A`, `FOGA_KEY_OPERATOR_A`, …) overriding one role. Keys never leave the kernel: the skill worker (below) is started with an environment reduced to `PATH`.

A **node** plays one part and holds one key, its cell's operator (`src/node/keys.ts`, `loadOperatorKey`): `FOGA_OPERATOR_KEY_FILE` names a file holding the key — a regular file owned by the node's user and readable by nobody else (mode 0600 or tighter) — or `FOGA_OPERATOR_KEY` holds the key itself; exactly one of the two. There is no phrase fallback: a node whose environment also carries `FOGA_MNEMONIC`, `FOGA_MNEMONIC_FILE`, `FOGA_DEPLOYER_PK`, `FOGA_OWNER_KEY[_FILE]`, `FOGA_GUARDIAN_KEY[_FILE]` or any `FOGA_KEY_<ROLE>` refuses to start and names the variables (never their values), because a process that can derive or sign for the owner, the guardian or the treasury is not a node holding its operator key alone. The owner's and the guardian's keys are read the same way (`FOGA_OWNER_KEY[_FILE]`, `FOGA_GUARDIAN_KEY[_FILE]`, `loadRoleKey`) by the CLI's one-shot commands in the operator's own shell — a birth, a migration, a rotation, a suspension — never by a running node. `foga keys export --role operator.A --out <file>` writes that file (0600) from the operator's phrase, in the operator's shell, for the node's separate OS user to own; `foga keys check` reads the current environment as a node would. The account the key operates is what bounds it: revision 2 of FogaCellAccount allow-lists what the operator may call and refuses it every asset-moving selector (docs/cell-account.md), so a stolen operator key can do what the cell does, in the cell's scope, under its daily cap — and nothing else.

W is the treasury. Before every step the genesis tops up each role whose balance has fallen below half its floor (`src/genesis/funding.ts`: a gas budget per role measured on the Sepolia run of 2026-11-01 with a margin of one half — 721 M gas for the twelve roles, 4.4 times what anvil's older gas schedule charges for the same operations — priced at the fee the chain quotes when the step starts; fixed floors on anvil, where only the judges beyond the pre-funded accounts need anything) and gives each cell its working capital at birth. The amounts are memoized facts, so a resumed run rebuilds the same transfers. `foga genesis preflight` prints the plan and what W must hold without sending anything; `foga world deploy` checks the deployer's balance against a budget of 11 M gas per contract before the first deployment (docs/genesis.md, "Running on a public chain").

## Running a skill

Before a cell executes a skill it holds, the kernel rebuilds the package from the local directory and compares `mdHash` and `packageHash` with the token's on-chain commitment (`skillOf`); a tampered file changes both and the run is refused. The two built-in executors then run in the skill worker, a separate process (`src/genesis/skill-worker.ts`, started by `src/genesis/skill-runner.ts`): `foga-probe` makes view calls against the world at a pinned block, `finch-extract-verify` extracts and checks a document deterministically — the extraction runs there too since 0.6.0, not in the kernel's process. The worker holds no key; its environment is reduced to `PATH` (it inherits no `NODE_OPTIONS`, so nothing can be preloaded into it), its heap is capped (512 MB), its run has a time limit and its output a size limit (1 MiB; over either it is killed), and outside the development loader it runs under Node's permission model with read access to the directories the job names and nothing else. A document path is accepted only inside the input directory the parent names, a fields file only inside the skills directory (real paths, so a link cannot point outside). The parent receives one JSON answer on stdout and decides what to commit to. That is what the boundary is: a process with the least the job needs, not a sandbox for arbitrary code — the node's executors are these two, and docs/design-memo.md says so where it describes what a skill may run.

## The prover

Both ZK paths of ERC-8419 run through `prover/run.cjs`: a stdin/stdout bridge over the upstream prover (`vendor/kya-standard/companions/zk-kya-groth16/prover.js`, with the credential circuit's wasm and proving key next to it) and over FOGA's own predicate circuit (`zk/build`, docs/zk.md). `prover/` is a sub-package with its own dependencies (snarkjs, circomlibjs; `npm run zk:install`), so the kernel's own dependency tree stays at ethers. The bridge keeps the roles apart: `commit` (the prover's Poseidon commitment to its secret), `attest` (the attestor signs the credential over the commitment, never seeing the secret), `root` (an issuer or source set from keys), `prove` (the credential proof: the prover's secret plus public material only), `record.sign` (a source signs one task-completion record) and `predicate.prove` (the predicate proof: the records with their signatures, the prover's secret, public material). FOGA's attestor and source keys and the cells' prover secrets are derived from the signers' keys, so a run is reproducible and nothing extra is stored; a resumed run reuses the recorded proofs.

## `node:sqlite`

Node 22 ships `node:sqlite` unflagged but still prints an experimental notice on first load. The store silences that one notice during its own load and nothing else; Node 24 prints none.
