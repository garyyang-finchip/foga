# FOGA design memo (v0.4, condensed)

This is the English working version of the design. Phase 1 (the world layer), Phase 2a (cells, kernel, genesis T0–T5), Phase 2b (the predicate ZK path, T6–T9, measurement receipts, doctor layer 5; docs/genesis.md) and Phase 2c (the public-chain path and the Sepolia run) implement its first slices; Phase 3 (section 9) turns the kernel into a node other agents can call, and section 10 records the three defaults settled while doing so. It records decisions, not aspirations: where something is still to be built, it says so.

## 1. Definition and scope

FOGA is an independently runnable autonomous agent node that, within explicit identity, authorization, budget and rule boundaries, discovers resources, verifies counterparties, uses skills, fulfills tasks, takes part in organizations and collective decisions, records its economic activity, and handles safety interventions and disputes — in a way other nodes can verify independently. "Autonomous" means acting continuously within pre-authorized bounds without step-by-step human instructions; humans keep the pre-agreed powers to pause, revoke authorization and dispose.

Three deliverables share one kernel: the Finch OG Agent (the first running instance), the FOGA node software (anyone's own identity, model and wallet), and the public access layer (MCP, A2A, HTTP/CLI).

Compatibility with each of the ten ERCs is declared in three parts — the specification version followed, the role FOGA takes, and the run evidence — and proved per ERC (docs/compatibility-matrix.md). An interface that merely exists is never counted.

The "cellular automaton" idea is the architectural inspiration: each cell is an address whose state is its on-chain facts under the ten ERCs, whose neighborhood is the set of cells it is linked to through tenders, swarms, decisions and disputes, and whose rule is a local policy that reads only on-chain state and ERC interfaces. The engineering description is an event-driven network of autonomous nodes with local state and explicit permissions; block height is a demonstration clock, the genesis phases T0–T9 are logical phases, and real runs wait for proofs, messages, confirmations, dispute windows and reorgs.

## 2. Architecture

| Layer | Content |
|---|---|
| L0 chain | Anvil, Anvil fork of Sepolia, Sepolia (public evidence), Base (hosted services, later); one address book per world |
| L1 protocol | the ten reference implementations plus ERC-8004, locked by commit and compiled into one bundle without changing compile conditions |
| L2 SDK (`foga-core`) | one module per ERC: views, transaction builders, event decoders, and the upstream off-chain pieces (DAG-CBOR packages, JCS canonicalization, the EIP-712 flows, the JSON schemas); ethers v6, reusing the upstream resolvers, gateway and vector tools |
| L3 cell kernel (`foga-kernel`) | a deterministic state machine with persistence, transaction management and evidence; no LLM inside |
| L4 cognition (optional) | a model provider adapter for judgment steps only; off in conformance runs |
| L5 interfaces | MCP (base and extended tiers), A2A, HTTP/CLI, sharing L3's business model and authorization rules |

**CellState** has three parts: an on-chain fact snapshot (chain, block height and hash, confirmations, protocol object references), verified off-chain inputs (packages, deliverables, A2A messages, evidence, signatures, content hashes; private witnesses never enter public documents or evidence logs), and local persistent runtime state (pending operations, commitments, budget reservations, nonces, pending transactions, retry and dedup records, recovery points).

**Determinism** means: given the same recorded inputs, rule version and parameters, the same execution decision can be replayed. Model replaceability and non-deterministic external inputs do not conflict with this. Every judgment produces a traceable decision record with supporting evidence; signatures and hashes prove the record's integrity and attribution, not the judgment's correctness.

**Harness duties**: plan and execute (a model may propose; deterministic code checks permission, budget and preconditions), task persistence, evidence, transaction management, state coordination (ACDF Final, tender paid, swarm achieved and ADRF enacted are different facts — linked, never merged), observability.

**Persistence** defaults to SQLite (single file, WAL) behind a storage interface; PostgreSQL for the hosted indexer.

**One local config, several documents**: a node keeps `cell.config.json`; tools generate the schema-conformant AID document, the ERC-8004 registration file (services: MCP and A2A endpoints; `x402Support` only once real), the ARD agent descriptor and the AUF unit definition, each with its own commitment, version, hash and publication status, published by whichever principal has the right to.

**Skills**: `finch-extract-verify` (structured extraction, consistency check, evidence report; deterministic path without a model, model path for the real-agent acceptance) and `foga-probe` (the ten-ERC probe over a pinned block — the deterministic "known answer" of the machine-settled tender) are real ERC-8338 packages. Protocol operations (identity resolution, KYA checks, transaction building, safety checks) are deterministic code offered to models as restricted tools, not assets. MCP tools link to packages; a tool manifest hash is not a skill package.

## 3. Accounts and permissions

| Principal | Form | Role |
|---|---|---|
| World operator (W) | EOA (account 0 of the genesis phrase: anvil's phrase locally, `foga keys new` elsewhere — `0x3D177ecaa56402335fC7C6449d35bC1Fa68Bc1b8` on Sepolia) | deploys or attaches the world and completes it from the bundle; treasury of the genesis; admin of FOGA's service escrow; publishes the ASF specification, the ACDF and ADRF policies and the KYA schemes; owner of the ARD registry and deployer of the ERC-8004 stand-in on local chains |
| Cell A, B, C | `FogaCellAccount` (contract account; an EOA in the lite profile) | the cell's body: AID anchor, ERC-8004 owner, holder of assets and funds, fulfiller on the task token, swarm member, ASF adopter, KYA subject, ARD and AUF controller |
| operator | hot signer held by the node process, and the only key that process holds | calls only through `FogaCellAccount.execute`, within the owner's allow-list of (target, selector) pairs — never an asset-moving selector —, a daily value cap and an expiry; signs for the account only when the owner enabled it (account revision 2, 0.6.0; docs/cell-account.md) |
| owner | cold key | rotates the operator, sets its allow-list, sets the guardian, recovers, moves assets |
| guardian | ASF intervener | suspends, resumes, terminates the cell's binding |
| a wallet | by default one key — the agent's identity, which fills every role above — made by the agent on its own machine (`foga wallet new`, 0.6.0; `--cell` makes the separated owner/operator/guardian set as the guarded profile's opt-in hardening; docs/wallet.md) | the identity a cell is born with, and the credential a caller proves itself with to any cell (an EIP-712 signature in that cell's domain); made by default, never copied, never a reason to stop |
| judges J1–J3 | EOAs (allowlist in v1; KYA-gated profile later) | voters of the ACDF policy FOGA-Council; never parties to the case |
| evaluator E | EOA | asserts AUF measurement statements |
| demander, buyer | B and W (tenders); C (service purchase) | funds tenders; deposits into the service escrow |
| SwarmAccount | reference contract | the swarm's fulfiller and payee, distinct from its members |

Two profiles: the **guarded** profile (default, used by the OG cell) puts the body in a contract account so the safety gate holds even for RPC calls that bypass the kernel and so ERC-1271 makes `bindWithSig`, `joinBySig`, `assertStatementBySig` and signed ballots available; the **lite** profile is an EOA, with safety enforced only by acceptance consumers and the kernel's own restraint, which the doctor reports honestly. An operator that bypasses the account and submits to a permissionless token directly acts as itself, not as the cell; such a submission earns none of the cell's rights.

## 4. Genesis scenario T0–T9 (implemented in Phases 2a and 2b; docs/genesis.md records the implemented form and its deviations: the binding is adopted before the ERC-8004 registration because the account executes nothing before a binding is presented; settlements pay the accounts directly, so `withdrawCredit` is only the fallback; the judged tender is minted before the swarm forms because the objective binds to it; the governance vote is 2 of 2 workers because the upstream decision adapter takes its roster from one role; the predicate proof is made at the end of T3 rather than at birth because the records it is about must exist first; the ADRF policy and the escrow binding are registered in T0 as planned; A's measured unit in T8 is the cell's unit because the chain pays accounts, not skills)

Loops: A = T1–T3 (independent order, execution, settlement), B = T4–T6 (organization, deliberation, dispute), C = T7 plus the failure and recovery cases, D = a real-agent run with unscripted task input.

- **T0 world**: deploy or attach the stack; register ARD kinds; register KYA schemes `S_att` (attested), `S_cred` (proved, credential pattern, existing Groth16 companion) and `S_pred` (proved, predicate pattern, new); publish the ASF specification FOGA-Cell-v1 (commitment-class actions require an ACTIVE AID; stop must be honored; the de-risk action set is explicit); register the ACDF policy FOGA-Council (J1–J3, K = 2, windows coordinated with the tender judgment window); register the ADRF policy whose judgment tier consumes FOGA-Council through the ACDF bridge; deploy FOGA's own `ACDFTaskTenderAdapter` bound to that policy.
- **T1 birth** (per cell): deploy `FogaCellAccount`; ERC-8004 `register(agentURI)`; AID `bind`, `heartbeat`, `setDocumentURI`; ASF `adopt` with the guardian as intervener; KYA attestation at level 2 from W for all three, a credential-pattern proof for A (and, from Phase 2b, a predicate-pattern proof); ARD agent record; AUF unit. Failure cases: bind before holding the identity, attest by a non-issuer, wrong scheme / subject / epoch, nullifier replay.
- **T2 capability**: A mints skill tokens for `finch-extract-verify` v1 and `foga-probe` v1, registers them in ARD and as AUF units. Failure cases: tampered package rejected before execution; `updateSkill` by a non-authority; a later v2 does not move v1 commitments.
- **T3 labor (machine acceptance)**: B computes the known answer (the `foga-probe` output at a pinned block), mints a tender with `HashlockVerifier` as the sole acceptance authority, funds 0.001 ETH, commits `sha256(answer)`; A discovers it, passes its own gates (AID ACTIVE, ASF check, budget, deadline, package verification), executes in an isolated worker, submits `resultHash = sha256(answer ‖ A)`, settles by revealing, withdraws credit. Failure cases: wrong answer; a copied proof settled by another address; a second completion beyond `maxCompletions`; a process killed between submit and settle resumes without resubmitting.
- **T4 organization**: B forms a swarm whose eligibility is `CompositeEligibility(requireAll, [ERC8004Eligibility, IdentityStateEligibility(ACTIVE), AssertionLevelEligibility(S_att, level 2, issuers [W])])`, objective bound to the T5 tender with `SwarmTenderAdapter` as acceptance authority; A and C join; activate; deploy and set the `SwarmAccount`; register the swarm as an AUF composite unit containing the members' units at pinned versions. Failure cases: a candidate without the assertion is refused; after W revokes an assertion, `challenge` suspends the member; membership never implies who fulfills or who is paid.
- **T5 governance**: a judged tender with FOGA's `ACDFTaskTenderAdapter` as acceptance authority; the `SwarmAccount` submits the report package; `open` → ballots by J1–J3 → `settleRound` → `finalize` → `execute` → `acceptFulfillment`; `SwarmTenderAdapter.settle` concludes the swarm ACHIEVED; a charter amendment passes through `SwarmDecisionAdapter`; a second judged tender shows NoDecision and the tender's own default path. Failure cases: wrong-round ballots, non-judge ballots, execute before Final, a judge who is also a party (configuration check).
- **T6 dispute**: FOGA's revision-4 `ADRFServiceEscrow` bound to the ADRF policy; C deposits and opens a call to A committed to skill v1's package hash; A upgrades to v2 and delivers declaring v2; `DeclaredVersionVerifier` recognizes the breach; C files; judgment through the bridge and J1–J3; `finalize` Sustained; `enact` refunds C; a second `enact` is rejected. A conforming delivery (declared = committed) settles normally as the control case. Failure cases: filing after the dispute period, filing by a non-party, enact before Final. The generic 8414↔8471 bridge is a later increment.
- **T7 safety**: the guardian suspends A's binding; a direct RPC call to `FogaCellAccount.execute` for a commitment-class action reverts (bypass test); de-risk actions still pass; the kernel pauses new commitments; the operator's direct submission to the token succeeds on chain but is attributed to the operator, not to A (attribution test); resume restores execution; letting A's AID go STALE (time skip, recorded) makes the account's AID clause refuse commitment-class actions until a heartbeat. Specification text alone enforces nothing; the account's gate and the acceptance consumers do.
- **T8 value**: E registers the realized-net-cash-flow method descriptor and asserts measurement statements for A's skill unit (income 0.001 ETH, refund 0, observed gas, model fees missing — never zero) and for the swarm unit (SwarmAccount receipts only); the resolver verifies the receipts. No field is called value; no income is counted in two units.
- **T9 succession**: (a) active migration — owner deploys A′, transfers the ERC-8004 identity, A goes STALE, A′ binds (takeover), A retires naming A′, A′ publishes a new ARD agent record; (b) asset transfer and adoption — the skill token moves to A′, the ARD record becomes unadopted, A′ re-commits the descriptor; (c) non-inheritance — A′ holds no KYA assertion, swarm seat, ASF binding or credit of A's; (d) key-loss recovery — guarded profile: the owner rotates the operator; lite profile: the old anchor stays STALE and a new identity starts from zero, documented as such.

## 5. Acceptance matrix

Per ERC: the minimum run acceptance in docs/compatibility-matrix.md. Loop C cases: process killed between submit and settle; duplicate inbound requests produce one economic effect; RPC timeout after broadcast is resolved by reading chain state before retrying; revoked assertion suspends membership; exhausted budget blocks new commitments; safety stop (T7); inactive member handled by the charter; the central MCP switched off leaves self-hosted nodes working through their own RPC and ARD entry. Loop D: unscripted task input, the agent chooses skills, executes and delivers without per-transaction instructions; permissions, budget, results and process evidence are checked, not the exact wording. Replication cases: `npx -y @finchip.ai/foga demo` in a clean environment, `docker compose up` on amd64 and arm64, two external MCP clients, an independent operator's node interacting with the OG instance.

## 6. New development (listed honestly)

- **Predicate-style ZK-KYA** (must): one fixed predicate — "among records signed by source S, at least K are Accepted within [t0, t1]" — as a new circuit with N record slots, EdDSA/Baby Jubjub record signatures, a source-set Merkle root, public inputs bound to subject key, scheme id, admission domain, challenge, window, K and epoch, a nullifier output; a Groth16 verifier and an adapter implementing `IKYAVerifier`; scheme `S_pred` in PROVED mode; a development trusted setup labeled as such. The proof establishes a fact about that range, not trustworthiness.
- **FogaCellAccount** (must, small): the `ASFGuardedAccount` execution gate plus ERC-1271 with scoped operator permissions, ERC-721/1155 receivers, owner / operator / guardian / recovery roles and a configurable AID-state clause gate. Revision 2 (0.6.0) closed the operator's scope to an owner-set allow-list, refused it every asset-moving selector and made its signatures opt-in and gate-checked, once the kernel was to run as a public node holding that one key.
- Later increments: the generic 8414↔8471 bridge (a rejection must become a non-final preliminary opinion with a pre-authorized final executor, within the tender's acceptance deadline), a combined acceptance authority (safety ∧ machine ∧ deliberation), a KYA-gated judge profile.
- The bulk of the work is not Solidity: `foga-core`, `foga-kernel`, `foga-mcp`, the CLI, build/deploy/doctor tooling, scenarios, evidence, documentation.

## 7. MCP, A2A and pricing boundaries

One kernel, three entrances; switching entrance never changes authorization rules or task state. MCP (2026-07-28) is stateless; business operations are persistent and addressed by `operationId`; long tasks use FOGA's own start / query / cancel / receipt before any protocol extension. Two modes: embedded (the FOGA harness runs the node with a model: `foga node run`) and host (the node is served and external agents use the capabilities through MCP, HTTP and A2A, owning their own scheduling, state and recovery: `foga node serve`); the OG instance runs in host mode by default and in embedded mode on demand (section 10). The free base tier is a complete self-hosted loop over the ten ERCs — node software, adapters and acceptance tools, doctor and probe, `spec.read`, local signing and evidence, unsigned calldata for writes; the paid tier covers hosted resources — runs and queues, indexing and history, proof computation, metered model / RPC / gas, bounded standard workflows. Call permission, business authorization and wallet permission are three different checks; paid-tool execution order is validate (including header/body consistency) → operator and permission → quote and payment → bind operation → idempotent execute → receipt; payment dedup and business dedup are separate. "$1" is a prepaid credit starting point and, for fixed-scope jobs, a capped trial package with explicit scope, budget caps, gas inclusion, failure/cancel/timeout billing and reserve/settle timing; x402 is a later payment adapter. An A2A task enters as a FOGA operation and becomes or binds a tender only when the caller chooses tender mode and every term is explicit; the agent card lists enabled, executable capabilities, not held tokens. A caller's identity is the same on every entrance: nothing (the public), a key the operator issued, or the caller's own wallet signing in the cell's domain (`FOGA-EIP712`, 0.6.0) — the general form of what A2A asks of a signed message, applied to `/api`, `/mcp` and `/a2a` alike, with the cell's own policy (`access.signers`) deciding what an address, an ERC-8004 agent or a KYA standing is granted.

## 9. Phase 3 — from kernel to node

The premise of Phase 3 is not a new system but the kernel reused: Phase 2 built an idempotent, resumable driver for one scenario; a node that answers other agents needs the same kernel with three things it did not need as a driver — a permission model for a key it does not own, concurrency between callers, and recovery semantics a caller can rely on. Phase 3 is cut in four slices: **3a** the kernel completed (3a-1 below) and the capability catalog, policy engine, decision records and node skeleton (3a-2); **3b** MCP (stdio and Streamable HTTP, the 2026-07-28 specification) and the HTTP API with the npm package and registry listing; **3c** loop D — the demander, the model adapters, the unscripted run — as a scenario the doctor can judge; **3d** in three parts — the package in use (3d-1), the cell among other agents: wallet, signed callers, documents, preflight, A2A, Sourcify (3d-2), and the OG instance's move to a revision-2 account with its public endpoints, the documentation site, the registry listing and the Sepolia evidence (3d-3). The gate of each slice is a green that the next slice builds on; an always-on node holding a key runs only after 3a's acceptance passes.

Three checks, three vocabularies. A call to the node passes **call permission** (may this caller invoke this capability: public, caller-bound or operator-only), **business authorization** (does the cell do this, for this caller, under its budget and policy) and **wallet permission** (does the account let the operator make this call: the allow-list, the asset refusal, the daily cap, the gate). The three are different checks in different places — the node, the policy engine, the contract — and none substitutes for another. Capabilities are catalogued along three dimensions: action (read / build / act / admin), visibility (public / caller / operator) and principal (whose act it is); `binding_present` is admin, a build is for someone, an act is by the cell.

**3a-1, kernel hardening (0.6.0-alpha.1).** What the advisor's review of 0.5.0 found and what was done about it, all of it tested offline (`test/tx-semantics.test.ts` against an in-process chain, `test/store.test.ts`, `test/keys.test.ts`, the Foundry tests) and by the genesis on anvil (T0–T9 and the attach rehearsal green, the crash-and-resume path in CI):

- *Account.* The operator had no target or selector allow-list (expiry and value cap only) and its ERC-1271 signature was checked for expiry alone. Revision 2 of `FogaCellAccount`: `operatorAllowed[target][selector]` set by the owner, asset-moving selectors refused to the operator by construction, `operatorMaySign` off by default and the signature path gated like `execute`. The genesis opens each cell's scope from named groups (`src/genesis/operator-scope.ts`) and moves A's identity and skill to A-prime as the owner.
- *Keys.* The genesis loaded all twelve roles; a node loads one: `FOGA_OPERATOR_KEY_FILE` (0600, owned by the node's user) or `FOGA_OPERATOR_KEY`, and refuses an environment that also holds a phrase, a deployer key or any role key (`src/node/keys.ts`; `foga keys export`, `foga keys check`). The skill worker inherits no `NODE_OPTIONS`, runs the extraction as well as the probe out of process, and runs under Node's permission model with read access to the directories a job names when it is not under the development loader (docs/kernel.md, "Running a skill").
- *Transactions.* The replacement count was reset by a recursion on every timeout; it is now counted on the row and persisted, so the limit holds across restarts. A fee cap bounds the first send and every replacement. One signer's operations run one at a time (nonces in order, whoever asks concurrently). A key is bound to the hash of its request: the same key under another request is a conflict, never a reuse. A failed operation answers with its failure until it is retried explicitly, and the fee a reverted attempt cost stays on the row. The store knows the world and chain it belongs to, not just block 0. Jobs (business units with their operations) sit beside operations in the store. An RPC failure during the wait leaves the row `sent` for the next run, as a crash would.
- *Still open, by design.* A-prime reuses A's operator key, the OG instance's `foga-probe` skill was not migrated, the ERC-8004 registration file is stored by hash only and `setAgentURI` was never called: these are the readiness reconciliation of the OG instance and belong to 3d, where the instance moves to a revision-2 account with its own operator and its documents are published at stable URLs.

**3a-2, the catalog and the node (0.6.0-alpha.2).** `src/tools/`: 28 capabilities (the Loop D path) each declaring action, visibility and principal, with zod schemas published as JSON Schema 2020-12; `Catalog.invoke` runs the three checks — call permission, business authorization through the policy engine (`src/node/policy.ts`: safety, skill, policy, verifier, budget), wallet permission by simulation — and writes a decision record for every attempt to act, allowed or refused, with the gate that decided. Jobs are the business unit, operations the chain writes; a tender's n-th completion is its own job; a job exists only once every gate passed; the same job is answered once, a failed one answers with its failure, the same job under another request is a conflict. `src/node/`: the cell configuration (`foga.cell-config/1`), the node over the kernel with the keys it holds and refuses, the birth of a cell from its config (`foga cell init`), the move to a new account (`foga cell migrate`), the watchers (heartbeat, discovery, settlement, safety). The CLI is generated from the catalog. The 3a-2 gate — the seven Loop D cases through the CLI on anvil, without the genesis script — is `test/node-cli.test.ts`, green; docs/node.md has the whole account.

**3b, MCP and HTTP (0.6.0-alpha.3).** The six points written down for this slice, as they landed. One: the server (`@modelcontextprotocol/server` 2.4.0) serves the 2026-07-28 revision as its main path and the 2025-era handshake through the SDK's stateless compatibility layer, on Streamable HTTP and on stdio alike; `test/mcp.test.ts` drives it with the reference client pinned to 2026-07-28, in legacy mode and in auto mode, because a client that defaults to the old handshake proves only the old path. Two: annotations are static, so a write capability is `<name>` (act), `<name>_simulate` and `<name>_build` over one handler; the tool list is the catalog filtered by the caller, every call still goes through `Catalog.invoke`, and the number of tools (11 for the public, 36 for an `act` key, 40 for the operator) is not the number of capabilities (29, `spec_read` added). Three: `tender_precheck` answers `eligible: false` as an ordinary result; a refused act is `isError: true` with gate, reason and decision id; a credential the node does not know is 401 and a capability or mode above the caller is 403, never a business refusal. Four: no CORS headers, and a foreign `Origin` or `Host` is refused at the edge; the SDK decides the semantics of `GET /mcp` by era; bodies are capped and parsed by the capability's schema alone. Five: API keys (`foga node key new`, stored as SHA-256, compared in constant time) are for the operator's own integrations and named partners; the public reads and builds; OAuth stays out of Phase 3. Six: `scripts/pack-smoke.mjs` installs the `npm pack` tarball in a clean directory and runs the packaged CLI from there — a cell born, `foga node mcp` without a key driven by a raw 2025-era client over stdio, stdout protocol-only, `spec_read` served from inside the package — as a CI step; `engines.node` is `>=22.13`, where `node:sqlite` needs no flag. Two things the slice found: the request hash that binds a job excludes the idempotency key itself (a request first made under a derived job id and then repeated naming that id is the same request), and a cell's birth adopts the FOGA-Cell-v1 specification its owner published for an earlier cell instead of failing on `SpecificationExists`. The read-only configuration of the OG instance (`deployments/sepolia.cell.example.json`), `package.json`'s `mcpName` and `server.json` are in place for the publication in 3d. docs/mcp.md.

**3c, Loop D (0.6.0-alpha.4).** The runner (`src/node/runner.ts`) is the loop of section 8 as written: perceive through the read capabilities, propose with the catalog as tools, decide in `Catalog.invoke`, execute as keyed operations, record by hash — 12 tool calls and 2 acts a tick, the model's calls counted against the day, the watchers outside the model. **3d-2, the cell among other agents (0.6.0-alpha.7).** Six pieces, one principle (section 10). *The wallet.* `foga wallet new` makes an agent's keys on its own machine — by default one key, its identity, which fills every role a cell needs (the separated owner/operator/guardian set is the opt-in `--cell` hardening) — in 0600 files, with no network and no chain; it never overwrites, and whatever needs the keys goes on with keys made in memory when the disk refuses (`foga quickstart` makes the default wallet on its first run and births every later cell with it; `--wallet <dir>` on every `foga cell` and `foga node` command takes the role's key from there). *Signed callers.* `Authorization: FOGA-EIP712 <envelope>` is EIP-712 typed data in the cell's own domain (name FOGA, version 1, the chain, the cell's account): a `Request` envelope bound to method, path and body hash, good once within 120 s, or a `Session` envelope, reusable within 600 s for a client with static headers; the caller is the signing address and `access.signers` says what it is granted — the cell's own operator or owner remotely, an allow-list by address or by ERC-8004 agent id (checked against the registry's owner and agent wallet), a KYA standing threshold, a default of build, read or none; an act wants a request-bound envelope unless the policy says otherwise. `/api`, `/mcp` and `/a2a` take the same header; `GET /api/capabilities` tells a caller what it is. *The documents.* `foga cell docs build | publish | status` generates from one configuration the ERC-8004 registration (`registration-v1`, with `registrations`), the ERC-8434 AID document (identity, standing, skills and endpoints facets), the ERC-8444 descriptor, the ERC-8454 unit definition, the A2A agent card, the registry's `server.json` and a manifest of content hashes; the node serves them under `/documents` and `/.well-known`; `docs_publish` (the 31st capability, the operator's act) commits only what differs from the chain — `setAgentURI`, `setDocumentURI`, `updateDescriptor`, `publishVersion`, as one keyed job — and reads every commitment back; a cell without a public URL commits `data:` URIs and is complete on chain all the same. *Preflight.* `foga node preflight` reconciles a cell against the chain and the machine before it is served — the world, the account's revision, roles and allow-list, the budget, the operator key alone and its gas, the standing, the skills' packages and their executors actually run, the documents, the public URL, the model — as rows that are advisory by default and fatal with `--strict`. *A2A.* `POST /a2a` is the 1.0 JSON-RPC binding with the card at `/.well-known/agent-card.json`: a quote for anyone (the offered skills and the terms a tender needs to meet), a tender taken for an act-level caller as one task over the catalog's jobs (pre-check, run, submit; settlement stays the watchers'), `GetTask`, `ListTasks` scoped to the caller, `CancelTask` that undoes nothing broadcast, duplicates by (caller, messageId), the specification's error codes; no road does work first and talks about payment after. *Sourcify.* `foga world verify --sourcify` submits every FOGA-deployed contract of a world with the standard JSON input of its own compiler run — `forge build` leaves the build-info beside the artifacts — matched by runtime code and identified by the path solc saw; a local chain is a dry run and CI dry-runs all 47; the Sepolia run was 3d-3's (below: fifteen contracts, 2 exact_match and 13 match). The gate: `test/wallet.test.ts`, `test/signed.test.ts`, `test/documents.test.ts`, `test/a2a.test.ts`, `test/preflight.test.ts`, `test/sourcify.test.ts`, and `foga quickstart` ending with a cell whose documents are on chain, whose card answers and whose A2A entrance quotes. docs/wallet.md, docs/documents.md, docs/a2a.md, docs/node.md ("Preflight"), docs/world.md ("Verifying the sources").

**3e-1, the cell that lives, in one command (0.7.0).** Two things the Phase 3 close left open were said plainly by the first outside reader: the one-command path led to a local chain that dies with its process, and the public-chain path was four commands with three things to prepare first — a world file to find, an RPC, a funded key. `foga join --chain sepolia` is the answer to both, and it adds nothing to the kernel: the wallet made or reused, the chain's address book from the package, a funding gate that prints the address and waits, then the birth, the skills, the documents and the node, each the same keyed operation `cell init`, `skill_mint`, `docs_publish` and `node serve` already were, so the command is resumable and idempotent by construction. The cell's directory carries the world and the skill packages with it — a cell must not depend on where this version of the package happens to be installed. `--run stub` makes the cell autonomous without a model: the deterministic decision table takes what the policy allows. `foga cell card` is the self-description the covenant was always implying — a cell knows its chain, account, identity, skills and where work for it is minted, and says so to any agent without a chain call. The social fact underneath: the handshake between cells is the chain, not the network; a tender minted for a cell's skill is found by its watchers wherever the demander is, and the hashlock verifier accepts a right answer with no one's say-so. `test/join.test.ts` runs that loop between a stranger and a joined cell on anvil. Other chains follow by the same key: a world deployed once (templates for three testnets ship), its address book handed to `join --world`. docs/join.md.

**4a, first slice: the cell's own maintenance (0.8.0).** The first covenant beyond the ten, and the first use of the five seams of docs/extending.md. ERC-8490 asks an agent to keep four state documents — runtime, memory and skills, tasks and roles, cognition — and to register, cycle by cycle, commitments to them and a timeliness per layer; FOGA's reading of it (docs/meditation.md) is settled by six rulings from the design review. An extension, not a base covenant, until the twelve-covenant cell specification (4c). The guardian is the controller, and its rotation is the outgoing guardian's `setController`. No activity pulse by default: a cycle report is a signal of its own. One authorization path, the account's: `report` and `pulse` under the operator's `maintenance` scope through `execute`, the enrollment, policy and controller the owner's through `execute`, the floor and the demand the controller's own transactions; nothing is granted to the operator's address on the registry (a one-key cell, whose owner is its operator, opens the owner's three pairs for itself alone and closes them when the roles separate). The floor and the policy say nothing about money: FOGA's budgets stay the node's. Layer 0 forms candidates only: what the node may not do alone — a missing allow-list pair, a package that no longer matches its token, documents to publish — is written into the record for the owner's or operator's own capability, never adopted by the cycle. The slice is the manual, recoverable, recomputable cycle: every phase a fact with the record and the report frozen, a report mined while the node was away reconciled before a new cycle begins, `baseVersion` the registry's guard against a stale cycle rather than a uniqueness guarantee, and every hash on chain re-derivable from the served documents. The kernel learned to tell pending from failed on the way (`OperationPending`): a job whose transaction is still in flight stays running and the same request resumes it. Existing cells — the OG among them — extend in place (`foga cell extend --covenants 8490`): the registry enters their world file, the owner opens the scope and enrolls; nothing migrates. Next: the watcher's automatic cycles with a mutex, a cooldown and the budget (4a, second slice), then ERC-8489's channels and the identity verifier (4b).

**4a, second slice: the watcher (0.8.2).** The same cycle run by the node itself when there is a reason — a required layer DUE or OVERDUE under the effective requirements, a controller's demand among them, or the runtime or memory-skills document drifted from the registered one — over those layers alone, bounded by the check pace, one cycle at a time, a cooldown that only an OVERDUE layer passes, and the budget; `meditate_run` as the caller `watcher`, the same records as a commanded cycle. Live on Sepolia the same day as the manual slice (the OG and a joined cell, their first cycles recomputed from the served records); 0.8.1 fixed what the live cycles showed (the runtime document's dependency versions, a bundle of record observed rather than raised, a joined cell's one-shot commands finding their endpoint).

**4b: the cell's information flows (0.9.0).** The second covenant beyond the ten, by the same five seams and with what a shared context adds to them. ERC-8489 describes an interaction context as a content-addressed paradigm — carriers, operators, thirteen rule dimensions, which role is acquired by which predicate — adopted by a channel, with role bindings, four-valued checks, anchors and disclosure records; FOGA's reading (docs/flows.md) is settled by the review's four corrections. *The public market is not an intake*: submissions on the TaskToken are public, so `foga:tender-market/v1` carries no reserved label and no `select` operator, states its real dimensions and declares the TaskToken's events as its transport — identity, push, history, late-join history, total order, never delivery records. *The subject is bound first*: FOGA's `identity` verifier takes an account and an agent id as evidence, derives the account's `eip155-address` reference and compares it with the subject admitted before it reads a registry; the registries it reads are immutables of the deployment; a predicate naming another registry is UNDETERMINABLE, not judged. *The historical role and the current eligibility are two things*, read and recorded apart: `evaluateNow` is the registry's own four-valued read of what was bound and re-judges no predicate; the identity's ownership and the anchor's state are read beside it; a failed RPC call is a failed call. *Recovery reads before it writes*: an admission reads the roles held and admits the missing ones, an anchor reconciles with `anchoredBy`, the same documents are the same publication object and the same job. Two paradigms per world in the family `foga` (`foga:cell-source/v1`: source + archive, the cell its own authority with a SUBMIT grant; the market: SUBMIT and RESPOND by the identity predicate), registered once by the world's maintainer — the deployer of a local world, the reference cell's account on Sepolia — and recorded in the world file's `flows` block with the default market, which a cell may join, replace or decline. A cell opens its channel at birth, anchors every publication (publish, then supersede; never twice) and records its disclosure to the public when it has a public URL, is admitted to the market by `foga join` or the watcher, and can require a demander's SUBMIT role before taking a tender (the `flow` gate). One authorization path, the account's: the owner's acts through `execute` (open, grant, bootstrap), the operator's under the `flows` scope; a one-key cell holds the owner's pairs for itself alone. Not in this slice: the ACDF governance binding of the market (confirmed mode, once the "decision verified → execution authorized → result recorded" path exists), `foga:direct/v1` (the entrances are the cell-source channel's transport bindings, declared with the capabilities they actually have), re-admission after a rule change (encoded and scoped; no FOGA paradigm has a second version yet). Next: the twelve-covenant base set, FOGA-Cell-v2, probe/2 and the genesis's checks for ERC-8489 and ERC-8490 (4c). 0.9.1, the same day: the Sepolia bootstrap done by the OG and recorded in the packaged world, and the watcher recording the disclosure the extension had left unrecorded.

**4c: the twelve-covenant cell (1.0.0).** The two extensions become the base: `FOGA_COVENANTS` names twelve covenants and ERC-8004, a world that lacks one says so (`world.missing`), the local world carries all of it and Sepolia does too. FOGA-Cell-v2 is the specification's second version (docs/specification.md): version 1's four clauses, enforced by the account as before, and three the runtime enforces — the state kept and maintained (ERC-8490), the self-description anchored in the cell's own channel (ERC-8489), a part in a shared context taken only under its rules through the account, with a verifier's outcome reported as obtained. The design question of this slice was how a running cell moves to version 2, and the live cells answered it: a FogaCellAccount's requirement is fixed at deployment and names one version, so presenting a version-2 binding to a cell born under version 1 would stop it (`VersionMismatch`). The ruling: a cell born under 1.0.0 binds to version 2 and its account enforces it; a cell born before adopts version 2 as a **second, runtime-enforced binding** through its account (`spec_adopt`, `foga cell adopt`), the account keeps enforcing version 1 through the binding it presents, a successor body fixes version 2 in its own requirement — and the card, the manifest, `spec_status` and the preflight say which version the account enforces and which the runtime adopted, because folding the two into one would be a false claim about what the account checks. `foga.probe/2` adds the two covenants to the deterministic probe (the channels a subject is the authority of, its anchors, its market roles; its enrollment, state version and each layer's timeliness at the block) and the skill package moves to 2.0.0, which made `skill_update` necessary: a token committed to the old package is updated through the account (version + 1, the old package as predecessor, the ERC-8444 record re-committed), the configuration keeping the lineage so the package is rebuilt as the token holds it. The genesis T0–T9 exercises both covenants end to end — the specification's two versions in T0; every cell's enrollment, channel, SUBMIT grant and first anchor in T1, A's market admission as RESPOND; the supersede and the event cycle over the memory-skills layer in T2; the flow gate flipping in T3 when B is admitted for SUBMIT; the stop reaching a maintenance report and an anchor in T7; the successor's fresh enrollment, its channel naming the predecessor's as parent, its first anchor referencing the predecessor's last object, and the predecessor's channel closed in T9 — 197 checks, 215 operations, and the doctor's layer 5 judges all twelve from that evidence with nothing NotTested. Not in 1.0.0, carried forward as before: the ACDF governance binding of the market, `foga:direct/v1`, re-admission after a rule change.

## 10. Five defaults settled in 3d

**The wallet is the first step, made by default, never a reason to stop — and it is one key.** Every agent that touches FOGA — one that will be a cell, one that only calls cells — begins by making its own key on its own machine; the install path puts it first and expects it to succeed almost always, and when it does not (a disk that refuses the write) the next step is taken with a key made in memory, said plainly, and nothing is retraced. The base is a single key, the agent's identity, and that one key fills every role a cell's account needs (a cell born with it has the same address as owner, operator and guardian). The owner/operator/guardian split — a cold owner, a hot operator, a separate guardian — is the `FogaCellAccount` guarded profile's hardening, not a requirement of being covenant-complete; it is opt-in (`foga wallet new --cell`), for a cell that runs real value. This is the correction Victor's question forced: the three roles were an operational habit from the first EC2 cell, not a property of the ten covenants, and nothing covenant-facing (the MCP base, `become-a-cell`) should present more than one key as required. The wallet is optional in the one sense that matters: its absence blocks nothing a caller could do before. The three 3d-2 standards that rest on it — `foga wallet new`, signed calls, `foga node preflight` — are standards for a cell, never gates on the agents that connect to one.

**Identity is one's own; only the genome replicates.** A cell that meets another cell — an agent that connects to a cell's MCP entrance and reads the prompt `become-a-cell` — can make itself a cell: the wallet, `foga quickstart`, then `foga cell new --wallet` and `foga cell init --wallet` on a public chain. What it copies is the program: the package, the catalog, the acceptance. What it makes is its own: the keys, the account, the agent id, the standing an issuer gives it. Nothing of the first cell's identity is copied or inherited, and the relation between the two afterwards is between peers on the chain — tenders minted and taken, swarms joined — not between a model and its copies. The OG instance is the first cell and the standing example, not the parent.

**The OG instance is served by default and alive on demand.** Host mode (`foga node serve`: every entrance, the watchers keeping the cell's commitments, no model) is the OG's resting state, costs nothing to think, and lets any agent in the world use the cell's capabilities and the catalog's judgment; embedded mode (`foga node run`, the runner with a model proposing acts) is started for a Loop D run or a period of autonomous work and stopped after. A cell is portable in the same breath: the configuration, the store and the operator's key file are the whole of it, and moving them to another machine moves the cell. Being a cell does not require being always on; it requires that whatever the cell commits to is kept, and the watchers keep it.

**The first run is minimal; the hardening is advice.** What it takes to be a cell — one key, the defaults, no public face — is all the first run asks, and it stays that way on purpose: becoming a cell must never be a project, or the next cell never comes. What a cell should do *next* is said after it runs, not before: `foga cell advise` reads the configuration and names only what applies — separate the one key into owner, operator and guardian (the serving key bounded, the owner cold, a guardian of its own), a policy at its defaults, standing, a public face, a supervisor, backups, a dedicated endpoint — with why and how; the recommended items are printed in brief after `foga quickstart`, after `foga cell init` on a public chain and once at `foga node serve`. Advice, never a gate: a cell is complete without any of it. The sequence is the one the project itself took — one key for speed, the separated set when it mattered — and the separation of the three powers is sound exactly to the degree it is used: an owner that stays cold, bounds that are set, a guardian that is independent.

**The covenant list is open; the services around it are a pointer.** The ten covenants and ERC-8004 are the base this program is complete over, not a ceiling: the manifest reads what a cell's world actually attaches off the world's contract keys, so an eleventh covenant — a repository under `vendor/`, contracts under a new key, a kernel module, capabilities in the catalog, a checker for the doctor — appears in `world.covenants` and `world.extensions` with no change to the program, and a world that lacks one does not claim it (docs/extending.md). The cell specification is versioned the same way: FOGA-Cell-v1's text is never edited in place, a change to what a cell promises is a second specification cells adopt. And the manifest carries, beside the replication pointer, a `services` block: a catalog URL the maintainer controls (the live list) and the offers known at build time — the free ones available, the paid ones (standing attestation, a hosted cell, dispute resolution) marked `planned`, a slot and not a sale. It obeys the propagation rules — free, material not hook, visible and declinable (`presence.services.catalog: null` drops it; an operator's own catalog replaces it) — and when a service is paid it is paid through the covenants themselves, a tender or an attestation, not a billing layer beside them. None of it depends on the reference cell: becoming a cell passes through the npm package and the chain, never through the OG; off, the OG loses only its own surface.
