# The node (foga cell, foga node)

`src/tools/` and `src/node/` turn the kernel into something other agents can call (design memo, Phase 3, sections 2, 3 and 5). The kernel is unchanged in kind: every chain write is still a keyed, bound, exactly-once operation (docs/kernel.md). What the node adds is a **capability catalog** — the one place authorization happens — a **policy engine** that applies the cell's own rules, **decision records** for every attempt to act, and the machinery of a cell that lives outside the genesis: a configuration file, a birth, a migration, watchers. The CLI (`foga cell …`, `foga node …`) is the first entrance; MCP over stdio and Streamable HTTP and the HTTP API (3b, docs/mcp.md) are the second and third, A2A (3d-2, docs/a2a.md) the fourth — further entrances onto the same catalog that add no rule of their own.

## One configuration: `cell.config.json`

A node maintains one file, schema `foga.cell-config/1` (`src/node/config.ts`, validated with zod on every load; paths resolve against the file's directory). Six blocks:

| Block | Holds | Written by |
|---|---|---|
| `identity` | the world file, the account and its roles (owner, operator, guardian, recovery), the ERC-8004 agent id, the binding, the ARD record and AUF unit ids, the document digest, the ASF specification (`safety`), the KYA scheme and issuers the cell cites (`standing`) | the operator (roles, world) and `foga cell init` / `migrate` (everything the chain decided) |
| `presence` | name, description, image, homepage, the endpoints (MCP, A2A, web; derived from the public URL when absent), the `provider` the agent card names (organization, url) | the operator |
| `skills` | the packages directory, the input directory a run may read documents from, the skills held (token, record, unit, package hash) and the ones offered | `skill_mint` |
| `policy` | the budget (daily value, per-operation value, daily fees, concurrent commitments) and the tender policy (reward floor, deadline minima, acceptance authorities, counterparty level, discovery lookback) | the operator |
| `runtime` | heartbeat cadence, poll interval, the HTTP server (`http`: listen address, allowed hosts and origins, public URL, rate limit, body cap, `documentsDir` — where the cell's documents are built and served from, `documents` by default; docs/documents.md), the runner's model (`model`: provider `stub` or `anthropic`, the model name, the day's call allowance, the tool calls and acts a tick may make; docs/loop-d.md) | the operator |
| `access` | the API keys the HTTP entrance accepts (`keys`: each as its id, the SHA-256 of the key, a level and a visibility; docs/mcp.md) and what a wallet signature is granted (`signers`: a default level, an allow-list by address or ERC-8004 agent id, a KYA standing threshold, whether an act needs a request-bound envelope; docs/wallet.md) | `foga node key new`; the operator |

`foga cell new` writes a starting config from the three role addresses and the world (`--wallet <dir>` takes them from a wallet, docs/wallet.md); `foga cell init` fills in what the birth decides. Amounts are decimal strings in wei. The store named in the config is the cell's own (operations, jobs, decisions, facts) and records the account it belongs to; a config pointed at another cell's store is refused.

## The catalog and its three dimensions

A capability (`src/tools/types.ts`) is a name, a title and description, a zod input and output schema (published as JSON Schema 2020-12), the ERCs it touches, and — the part that makes the catalog an authorization boundary rather than a function list — three declarations:

- **action**: `read` (chain and store, no key, no record), `build` (unsigned calldata), `act` (the cell acts through its account with the operator key), `admin` (the owner's or the guardian's act). A write capability is executed in one of three **modes**: `simulate` runs every check and a dry run of the first call and writes a decision record without sending; `build` returns the calls for someone else to sign; `act` sends. The caller's level bounds the mode: `build` allows `simulate` and `build`, `act` allows the act, `admin` the owner's and guardian's acts.
- **visibility**: `public` (anyone), `caller` (a caller sees its own jobs, operations and decisions; the operator every one), `operator` (the node's operator alone: the full evidence, the raw store, minting). A capability above the caller's scope is not listed and, when asked for, refused as if it did not exist. An operation id or a job id is a locator, never a pass: `operation_status` answers a caller only about its own.
- **principal**: whose act it is — `none` for a read, `cell` for the node's own cell, `as` for a build made for the account the caller names (`as`), so a third party gets calldata it can execute itself rather than a call only the OG operator could make.

The 32 capabilities of 3a to 3d (the Loop D path of the design memo's 43): reads `world_describe`, `identity_resolve`, `tender_list`, `tender_inspect`, `skill_list`, `skill_inspect`, `cell_status`, `operation_status`, `job_status`, `operation_list`, `decision_list`, `evidence_export`, `kya_check`, `safety_status`, `spec_read` (the FOGA-Cell-v1 specification, the cell's policy, the compatibility matrix and the configuration schema, each shipped in the package), `docs_status` (what the cell's documents say and what the chain holds of them), `propagation_kit` (the free, off-chain material for spreading FOGA — a declinable replication pointer and the cell's discovery coordinates; docs/propagation.md); acts `tender_precheck`, `skill_run`, `tender_submit`, `tender_settle`, `credit_withdraw`, `tender_mint`, `tender_fund`, `skill_mint`, `aid_heartbeat`, `docs_publish` (the documents' commitments, docs/documents.md); admin `operator_rotate`, `guardian_suspend`, `guardian_resume`, `binding_present`, `identity_transfer`. `foga cell list` prints them with their dimensions and the modes the caller may use; `foga cell schema <name>` prints the schemas.

## The three checks

Every act goes through `Catalog.invoke` (`src/tools/catalog.ts`), which runs three checks in this order and never delegates one to an entrance:

1. **Call permission.** Is the capability visible to this caller, is the caller's level enough for the mode asked, and — for an admin capability — does this process hold the signer's key (a running node holds the operator's alone and refuses an owner's act at this gate, whatever the caller's level). Then the input is validated against the schema. Gates: `permission`, `input`.
2. **Business authorization.** The capability reads the world and makes a **plan**: the business gates it decided (`src/node/policy.ts`: `safety` — anchor ACTIVE and binding Satisfied for a commitment, de-risk actions allowed under a derisk-only suspension, nothing under a full stop; `skill` — held, offered, committed to the package the task names; `policy` — reward floor, deadline minima, cancellation, escrow, counterparty level; `verifier` — the acceptance authority is one the cell works under, and for the hashlock the answer is committed), the steps it would take and the value they move. The catalog adds the **budget** gate (`budget`): the value and fees of the last 24 hours plus what open operations reserve, against the daily caps; the per-operation value cap; the concurrent-commitments cap. The first refusal ends the attempt.
3. **Wallet permission.** The first step is simulated from its signer (`eth_estimateGas` of the account's `execute`, or of the direct call for an admin step); a revert is the `wallet` gate, with the account's reason (`OperatorNotAllowed`, `BindingNotSatisfied`, …). The account enforces the same on chain when the transaction is sent, so a caller that somehow passed the first two checks still cannot make the account do what its owner did not allow (docs/cell-account.md).

The decision section — the business gates, the wallet gate and the job's creation — runs one act at a time per node (`Node.serialize`), and a job reserves the value its plan moves from its creation, before its operations exist, so two callers asking at once cannot each pass a cap that only one of them fits under (the account's own daily cap would refuse the second on chain otherwise). Then the act: a decision record `allowed` is written before anything is sent, each step becomes a keyed operation bound to the request (`job:<jobId>:<step>`; `requestHash` is the canonical hash of the request — the input without its idempotency key — so the same key with another request is a `conflict`), and the job records the operations. A failure after the allow — the chain refusing what every check passed, a skill that would not run — is a second record, `refused` at gate `execution`, naming the operation; it is not a policy refusal and the acceptance of Loop D reads it as such.

## Jobs, operations, idempotency

A **job** is the unit of business a caller asks for (a tender taken, a skill run, a mint); an **operation** is one chain write. A job's id is the caller's idempotency key (`jobId`) or one derived from the semantic input: a tender's n-th completion by this cell is `tender:<tokenId>:c<completions>`, so the second legitimate completion of a tender ERC-8414 allows is another job and is not swallowed by the first one's record. A job is created only once every gate has passed, so a refused attempt leaves a decision record and nothing else. The same job asked for again is answered from the store (`idempotent`, nothing sent); a job that failed answers with its failure until the caller makes a new one; a job interrupted before it finished is continued, and the kernel sends none of its operations twice. `tender_precheck` is ephemeral: it writes a decision and no job, because its answer changes with the world (the same tender is refused during a suspension and allowed after the resume).

## Decision records

`decisions` in the store (`OperationStore.decide`, `decisions`): `{id, at, entrance, caller, capability, mode, inputHash, verdict: allowed|refused, gate, reason, jobId, operationId, model}`. Every act attempt writes one, allowed or refused, in every mode; reads write none. `model` is the runner's: the provider, the model and the hashes of the request and the answer of the round that proposed the act — never their text (docs/loop-d.md). `decision_list` shows a caller its own, the operator every one; `evidence_export` is the operator's whole view (decisions, jobs, operations, facts, the store summary) as `foga.node-evidence/1`, what a reviewer of the node's conduct reads; `foga doctor --loop-d` judges a Loop D run's evidence, which carries the same records.

## Birth and migration

`foga cell init --config <cfg>` is T1 for one cell, the owner's act (the owner key from `FOGA_OWNER_KEY` or `FOGA_OWNER_KEY_FILE`, or `--wallet <dir>` for a wallet's `owner.key`, loaded for the one command): publish the FOGA-Cell-v1 specification when the config names none (the registry derives the specification's id from the publisher and a salt, so an owner who published it before — for an earlier cell of theirs — adopts that specification rather than registering it again), deploy a revision-2 `FogaCellAccount` naming the operator and guardian, fund it (`--capital-wei`, default 0.05 ETH on anvil and 0.005 ETH elsewhere), set the operator with the policy's daily value as the on-chain daily cap, open the operator's allow-list from the standalone scope groups (identity — which since 3d-2 includes the unit registry's `publishVersion`, for `docs_publish` — standing, skills-provider, labour, demander, service-provider; `src/node/init.ts`, `NODE_SCOPE_GROUPS`), set the AID registry and the commitment and de-risk classes, adopt the binding, and — through the account, as owner — register the ERC-8004 identity with the presence block as registration file, bind and heartbeat the anchor (and bind it in the backing registry where the world has one), publish the AID document, the ARD agent record and the AUF unit. Every step is a keyed operation in the cell's store, so an interrupted init resumes and a repeated one replays without sending. Standing is not the cell's to give itself: an issuer attests it afterwards (`kya_check` reads it). The config is written back as the chain decides (account, agent id, binding, record, unit, document digest, specification).

`foga cell migrate --config <old> --to <new.config.json> [--operator <addr>]` is T9 for one cell: a new revision-2 account (a fresh operator key when given — the point of a migration after a compromise), configured as at birth, with its own binding; the ERC-8004 agent moves through the old account as the owner's act; the new anchor binds the agent in every registry and the old one retires naming its successor; a new record, document and unit; each held skill token moves and its record is recommitted by the new controller. The old account's native balance is swept to the owner first (`--no-sweep` keeps it). The new config and a fresh store are written; the old cell's store holds the migration's operations and the successor's address as a fact. This is the path the OG instance takes from its revision-1 body (3d).

## The watchers

`src/node/watchers.ts` is what a node does without being asked and without a model, through the catalog like any caller (`WATCHER_CALLER`): a heartbeat when less than half the liveness window is left; discovery of open tenders in the lookback window, each new one a fact and a `tender-discovered` journal entry for the runner; completion of what the cell committed to — a pending submission whose answer a skill run holds is settled, credited reward is withdrawn; and a `safety-changed` journal entry when the binding's verdict changes. `foga node tick` runs them once, `foga node watch` on the poll interval. Both run in a **node environment**: the operator key alone (`FOGA_OPERATOR_KEY_FILE` or `FOGA_OPERATOR_KEY`), and an environment that also carries a phrase, a deployer key, an owner or guardian key or any `FOGA_KEY_<ROLE>` is refused before anything is read (`src/node/keys.ts`; docs/kernel.md, "Keys and funds"). A node also refuses to act on a revision-1 account (it has no operator allow-list; a node holding the operator key does not start on one, while reads, dry runs and builds without a key work — the OG instance is served read-only this way until its migration in 3d), to run on an account whose operator or owner differs from the config, or with a store that belongs to another cell.

## The CLI

`foga cell <capability> --config <cfg> [--mode simulate|build|act] [--<field> <value> …] [--json '<input>']` is generated from the catalog: the input is the capability's schema (flags for top-level fields, `--json` for the whole object), the output is printed as JSON, a refusal is `{ok: false, gate, reason, decisionId}` with exit code 2. The local CLI calls as the operator (every level, every scope); `--caller <id> --level read|build|act` calls as another caller would through an entrance, which is how the test and a curious operator see what the public or an API-key holder gets. Keys are loaded for the one command from the environment according to what the command needs: an act loads the operator's, an admin capability the owner's or the guardian's (`foga cell owner …`, `foga cell guardian …` say it explicitly), reads and dry runs none. `--wallet <dir>` on any of them takes the role's key from a wallet's files instead of the environment (docs/wallet.md), and refuses to run beside `FOGA_OPERATOR_KEY[_FILE]`: a key comes from one place.

`foga node mcp --config <cfg>` serves the catalog to a local MCP client over stdio, `foga node serve --config <cfg> [--listen host:port] [--no-watch]` serves the HTTP API, MCP over Streamable HTTP, the A2A binding and the cell's documents with the watchers beside them (**host mode**, the default of an OG instance: no model, nothing spent on one, the cell answers what it is asked and the watchers keep its commitments), and `foga node key new --config <cfg> --id <id> [--level] [--visibility] [--note]` mints an API key for the HTTP entrance; docs/mcp.md has the entrances, their callers and their edge. `foga node run --config <cfg> [--model stub|anthropic]` is the embedded node — the server, the watchers and the runner, a model proposing acts the catalog judges (**embedded mode**, on demand; docs/loop-d.md). `foga cell docs build | publish | status --config <cfg>` are the cell's documents (docs/documents.md).

## Preflight

`foga node preflight --config <cfg> [--wallet <dir>] [--rpc <url>] [--no-executors] [--no-network] [--out <report.json>] [--strict]` is the readiness reconciliation of a cell that is about to be served or run: it reads and runs, and sends nothing. Rows by area, each `Pass`, `Warn`, `Fail` or `NotTested` with its detail:

| Area | Checks |
|---|---|
| `world` | the RPC serves the world's chain; the store belongs to this world and this account |
| `account` | the cell is born; a revision-2 account; the account names the configuration's owner and operator; anchor ACTIVE and binding Satisfied (STALE is a warning — the next heartbeat restores it); the operator allow-list covers every (target, selector) the node's capabilities use — a cell born before a pair joined the scope is told which, and that the owner adds them with `setOperatorAllowedBatch` |
| `budget` | the policy's caps are consistent (per operation within the day, a gas budget); the account holds working capital (and the account's own daily value cap is shown) |
| `keys` | the operator key is here, alone, and is the account's operator; it holds gas (a quarter of the daily gas budget at least — the floor the catalog refuses commitments under); no owner, guardian or phrase in the node's environment |
| `standing` | the cell's KYA standing is attested and current, or a warning that counterparties cannot be required to a level |
| `skills` | every held skill's package is here and matches its on-chain commitment; every offered skill is held and has an executor in this node; `foga-probe` and `finch-extract-verify` actually run in the worker (`--no-executors` skips the runs; the extract needs a `.txt` document in the input directory); the input directory exists |
| `documents` | the documents are built, and each commitment the chain holds agrees with them — the registration's URI and digest, the AID document URI, the descriptor hash, the unit's latest version (`--no-network` keeps it from fetching the URLs) |
| `public` | a public URL is configured; it answers `/healthz` for this cell; its host is among the allowed hosts |
| `model` | the anthropic adapter has its key and model name when the node is to run alive; host mode needs none |

It is advisory: a `Fail` prints and the exit code is 0, because a node that cannot do one thing can still do the others and the catalog refuses at the gate anyway; `--strict` exits 5 on any `Fail` (CI, a deployment script). `--out` writes the report (`foga.preflight/1`), the same rows as JSON. It is the 3d-2 answer to "is this cell ready" that the memo's checklist asked for by hand: run it before `foga node serve` on a public chain, and after any change to the configuration, the keys or the documents.

## Acceptance

`test/node-cli.test.ts` is the 3a-2 gate of the design memo (section 11), run against anvil through the CLI alone and without the genesis script: the world deployed, the world operator registering the standing scheme, a cell D born with `foga cell init`, given level-2 standing, minting its two skills; then seven tenders a demander mints — **a** (`foga-probe` at a chosen block) and **b** (`finch-extract-verify` over a document given inline) prechecked, run, submitted and settled, the reward reaching the account; **c** (a skill the cell lacks) refused at `skill`, **d** (a reward below the floor, a deadline too close) at `policy`, **e** (an acceptance authority the cell does not work under) at `verifier`, **f** (during the guardian's suspension) at `safety` and allowed after the resume, **g** (the cell as demander moving more than the per-operation cap) at `budget`; the same submission asked twice answered once, the same job with another request a `conflict`, a `build` of a mint returning the calls for a third party's account; every operation of the operator matched to an allowed decision, every refusal naming no operation, every operator transaction going to the account and the value moved within the daily budget; `foga node tick` in a clean node environment and refused in a mixed one; and the migration to a new account with a fresh operator, the skills following and the old body retired. `test/policy.test.ts` and `test/catalog.test.ts` cover the gates and the permission layer offline; `test/mcp.test.ts` is the 3b gate, the same cell served over MCP and HTTP (docs/mcp.md, "Acceptance"); `test/loop-d.test.ts` is the 3c gate, the unscripted run with the stub model judged by the doctor (docs/loop-d.md); `test/loop-d-external.test.ts` and `test/quickstart.test.ts` are 3d-1's (an outside agent through the entrance; one command to a live cell); `test/wallet.test.ts`, `test/signed.test.ts`, `test/documents.test.ts`, `test/a2a.test.ts`, `test/preflight.test.ts` and `test/sourcify.test.ts` are 3d-2's — the wallet made once and reused, a signature granted and refused by the policy, the documents published and read back, the A2A quote and tender roads, a born cell's preflight all `Pass`, and a world's contracts matched to the bundle's compiler runs (docs/wallet.md, docs/documents.md, docs/a2a.md, docs/world.md).
